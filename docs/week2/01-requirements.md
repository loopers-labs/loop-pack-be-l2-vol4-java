# 이커머스 도메인 요구사항 명세서

---

## 1. 개요

- **목적**: 좋아요·주문으로 이어지는 감성 이커머스의 핵심 거래 흐름(브랜드/상품/좋아요/주문)을 정의한다.
- **배경**: 여러 브랜드가 입점한 감성 이커머스 서비스를 가정한다. 방문자는 가입 없이 브랜드와 상품을 둘러볼 수 있고, 로그인한 사용자는 관심 상품에 좋아요를 눌러 두었다가 마음에 든 여러 상품을 한 번에 주문한다. 운영자(어드민)는 브랜드·상품을 등록·수정·삭제하고 전체 주문을 조회해 운영 현황을 파악한다. 좋아요와 주문이 맞물리는 이 거래 흐름이 서비스의 중심이다.

---

## 2. 이해관계자

| 구분 | 설명 | 식별 방식 | 권한 |
|-------|------|-----------|------|
| 비로그인 사용자 | 가입 없이 둘러보는 방문자 | 없음 | 브랜드·상품 **조회만** |
| 로그인 사용자 | 좋아요·주문·쿠폰을 하는 회원 | `X-Loopers-LoginId` / `X-Loopers-LoginPw` 헤더 | 조회 + 좋아요 + 주문 + 쿠폰 발급/사용, **본인 데이터만** |
| 어드민 | 브랜드·상품·쿠폰을 관리하는 운영자 | `X-Loopers-Ldap` 헤더 | 브랜드·상품·쿠폰 관리, **전체 주문 조회** |

## 3. 용어 정의

| 용어 | 정의 |
|------|------|
| 브랜드(Brand) | 상품을 묶는 판매 주체. 하나의 브랜드는 여러 상품을 가진다. |
| 상품(Product) | 판매 단위. 하나의 브랜드에 속한다. 가격과 재고를 가진다. |
| 재고(Stock) | 해당 상품을 지금 몇 개 더 팔 수 있는지를 나타내는 수량. |
| 좋아요(Like) | 사용자가 상품에 표시하는 관심. **한 사용자-상품 쌍당 최대 1개**. |
| 멱등(Idempotent) | 같은 요청을 여러 번 보내도 결과 상태가 동일한 성질. 좋아요 등록/취소에 적용. |
| 주문(Order) | 한 사용자가 한 번에 요청한 구매 단위. 한 개 이상의 주문 항목으로 이뤄진다. |
| 주문 항목(Order Item) | 주문에 담긴 상품 하나와 그 수량. |
| 주문 이력 | 주문 항목이 주문 시점의 상품명·단가를 복사해 보관한 값. 이후 상품 정보가 바뀌어도 이 값은 변하지 않는다. |
| 쿠폰 템플릿(Coupon Template) | 어드민이 정의하는 쿠폰의 원형. 할인 종류(정액/정률)·할인 값·유효일수를 가진다. |
| 쿠폰(내 쿠폰, User Coupon) | 사용자가 템플릿으로 발급받은 쿠폰 한 장. 발급 시점의 혜택·이름·만료일을 복사(스냅샷)해 보관한다. 주문 1건에 1장 사용하며 재사용할 수 없다. |
| 정액 할인(FIXED) | 주문 금액에서 고정 금액(원)을 깎는 방식. |
| 정률 할인(RATE) | 주문 금액의 일정 비율(%)을 깎는 방식. 원 단위 미만은 절사한다. |
| 결제(Payment) | 한 번의 결제 **시도**. 외부 PG로 한 주문의 금액을 청구한 기록. 한 주문에 여러 결제(재시도)가 있을 수 있다. |
| PG(Payment Gateway) | 카드 승인을 대행하는 **외부 시스템**(본 과제는 pg-simulator). 우리 트랜잭션 밖에 있어 지연·실패·중복·응답 유실이 정상적으로 일어난다. |
| 결제 시도(attempt) | 사용자가 "결제하기"를 눌러 한 주문에 대해 결제를 한 번 요청하는 단위. 실패하면 같은 주문에 새 시도를 만들어 재결제한다. |
| 콜백(Callback) | PG가 처리 결과를 **우리 서버로** 비동기 통지하는 서버-서버 호출. 사용자 브라우저로 오는 것이 아니다. |
| 정산(Reconciliation) | 콜백이 유실되거나 PENDING이 오래 남았을 때, 우리 서버가 PG **상태 조회 API**로 결과를 확인해 내부 상태를 맞추는 복구 절차. |
| 이중결제 차단(따닥) | 같은 주문에 동시·연속 결제 요청이 들어와도 청구를 1회로 막는 것. 결제 예약 시 **주문 행 비관락(`FOR UPDATE`)** 으로 검사+저장을 직렬화하고, "살아있는 시도(`PENDING`·`SUCCESS`)가 있으면" 거부한다(`FAILED`만 있으면 재시도 허용). |
| 대기열(Waiting Queue) | 트래픽 폭증 시 주문 API **앞단**에서 유저를 줄 세우는 back-pressure 장치. Redis Sorted Set(score=진입 시각, member=userId)으로 순서를 보관하고, 행사 때만 켠다(`queue.enabled`). |
| 입장 토큰(Entry Token) | 대기열을 통과한 유저에게 발급되는 주문 입장 권한 증명. TTL(5분)이 있으며, 주문 **성공 시에만 소진**된다(실패 시 보존 → TTL 내 재시도 가능). |
| Thundering Herd | 같은 발급 총량이라도 한 번에 몰아 발급하면 그 인원이 동시에 주문을 때려 하류에 주기적 스파이크가 재현되는 현상. 발급을 짧은 주기(100ms)로 쪼개 평탄화한다. |

## 4. 기능 요구사항

> 각 기능은 "누가·무엇을·왜"를 한 문장으로 적고, 그 아래 **상세 동작 규칙**으로 구체 조건을 정의한다.

### 4.1 브랜드 · 상품 조회 (대고객)

#### US-01: 브랜드 정보 조회
방문자가 특정 브랜드의 정보를 조회해, 그 브랜드가 어떤 곳인지 확인하고 상품을 둘러볼 수 있게 한다.

**상세 동작 규칙**
- **AC-01-1**: 존재하는 브랜드를 조회하면, 브랜드의 고객 노출 정보(이름, 소개 등)를 보여준다.
- **AC-01-2**: 존재하지 않거나 삭제된 브랜드를 조회하면, "브랜드를 찾을 수 없음"이라고 안내한다.

#### US-02: 상품 목록 조회
방문자가 브랜드·정렬·페이지 조건으로 상품 목록을 조회해, 원하는 상품을 효율적으로 찾을 수 있게 한다.

**상세 동작 규칙**
- **AC-02-1**: 아무 조건 없이 목록을 요청하면, 기본 정렬(최신순)과 기본 페이지(첫 페이지, 20개)로 상품 목록을 보여준다.
- **AC-02-2**: 브랜드를 지정해 목록을 요청하면, 해당 브랜드의 상품만 보여준다.
- **AC-02-3**: 정렬 기준(최신순 / 가격 낮은순 / 좋아요 많은순)을 지정하면, 그 기준으로 정렬해 보여준다.
- **AC-02-4**: 조건에 맞는 상품이 하나도 없으면, 빈 목록을 정상적으로 보여준다.

#### US-03: 상품 상세 조회
방문자가 특정 상품의 상세 정보를 조회해, 구매 여부를 판단할 수 있게 한다.

**상세 동작 규칙**
- **AC-03-1**: 존재하는 상품을 조회하면, 상품명·가격·브랜드 정보·좋아요 수·판매 가능 여부를 보여준다.
- **AC-03-2**: 존재하지 않거나 삭제된 상품을 조회하면, "상품을 찾을 수 없음"이라고 안내한다.

---

### 4.2 좋아요 (대고객 · 멱등)

#### US-04: 상품 좋아요 등록
로그인 사용자가 마음에 드는 상품에 좋아요를 눌러, 나중에 다시 찾아보고 자신의 취향이 서비스에 반영되게 한다.

**상세 동작 규칙**
- **AC-04-1**: 아직 좋아요하지 않은 상품에 좋아요를 누르면, 좋아요가 등록되고 그 상품의 좋아요 수가 1 늘어난다.
- **AC-04-2**: **이미 좋아요한 상품**에 같은 요청을 다시 보내면, **오류 없이 성공으로 처리**하며 좋아요 수는 그대로 유지된다(멱등).
- **AC-04-3**: 존재하지 않는 상품에 좋아요를 누르면, "상품을 찾을 수 없음"이라고 안내한다.
- **AC-04-4**: 로그인하지 않은 상태에서 좋아요를 누르면, 요청을 거부한다.

#### US-05: 상품 좋아요 취소
로그인 사용자가 좋아요를 취소해, 더 이상 관심 없는 상품을 정리할 수 있게 한다.

**상세 동작 규칙**
- **AC-05-1**: 좋아요한 상품의 좋아요를 취소하면, 좋아요가 제거되고 그 상품의 좋아요 수가 1 줄어든다.
- **AC-05-2**: **좋아요하지 않은 상품**에 취소 요청을 보내면, **오류 없이 성공으로 처리**하며 좋아요 수는 그대로 유지된다(멱등).
- **AC-05-3**: 좋아요 수는 어떤 경우에도 음수가 되지 않는다.
- **AC-05-4**: **존재하지 않거나 삭제된 상품**에 취소 요청을 보내도, 그 상품에는 좋아요가 없으므로 **오류 없이 성공으로 처리**한다(AC-05-2와 동일하게 멱등). 좋아요 등록(AC-04-3)이 "상품을 찾을 수 없음"으로 거부하는 것과 의도적으로 다르다 — 취소는 "상품이 없으면 좋아요도 없다"는 관계라 좋아요 유무만으로 판정한다.

#### US-06: 내가 좋아요한 상품 목록 조회
로그인 사용자가 자신이 좋아요한 상품 목록을 조회해, 관심 상품을 한곳에서 확인할 수 있게 한다.

**상세 동작 규칙**
- **AC-06-1**: 로그인 사용자가 본인 좋아요 목록을 요청하면, 좋아요한 상품 목록을 페이징하여 보여준다.
- **AC-06-2**: 다른 사용자의 좋아요 목록을 요청하면, 요청을 거부한다(타 유저 정보 직접 접근 불가).

---

### 4.3 주문 (대고객)

#### US-07: 주문 생성
로그인 사용자가 여러 상품을 한 번에 주문해, 원하는 상품을 실제로 구매할 수 있게 한다.

**정상 흐름 요약**: 주문 요청 수신 → 상품·재고 확인 → (쿠폰 지정 시) 쿠폰 검증·할인 계산 → 재고 차감 → 쿠폰 사용 처리 → 주문 생성.

**상세 동작 규칙**
- **AC-07-1**: 주문 요청은 1개 이상의 주문 항목(상품·수량)으로 한다. 존재하지 않는 상품이 포함되거나 수량이 1 미만이면 주문을 거부한다.
- **AC-07-2**: 모든 상품의 재고가 충분하면, 각 상품 재고가 주문 수량만큼 차감되고 주문이 **생성**(`CREATED`) 상태로 저장된다.
- **AC-07-3**: 재고가 하나라도 부족하면, **주문은 생성되지 않으며**, 어떤 상품이 부족한지 안내한다.
- **AC-07-4**: 재고 차감과 주문 생성은 하나의 처리 단위로 묶인다 — 재고 부족으로 주문이 거부되면(AC-07-3) 재고는 변동되지 않는다.
- **AC-07-5**: 주문에는 주문 시점의 **상품명·단가가 이력으로 저장**되어, 이후 상품이 수정·삭제되어도 주문 상세 내역은 변하지 않는다.
- **AC-07-6**: 주문 시 **쿠폰을 0장 또는 1장** 지정할 수 있다(주문 1건당 최대 1장). 쿠폰을 지정하면 주문 시점의 **적용 전 금액·할인액·최종 금액이 이력으로 저장**된다. 쿠폰을 지정하지 않으면 할인액은 0이고 최종 금액 = 적용 전 금액이다.
- **AC-07-7**: 지정한 쿠폰이 **본인 소유가 아니거나, 이미 사용됐거나, 만료됐거나, 최소 주문 금액에 미달하면** 주문을 거부한다. 거부 시 재고·쿠폰 모두 변동되지 않는다(AC-07-4와 동일한 처리 단위).
- **AC-07-8**: 주문이 성공하면 사용한 쿠폰은 **사용 완료(USED)** 상태가 되어 **다시 사용할 수 없다**(재사용 불가). 사용 처리와 주문 생성·재고 차감은 하나의 처리 단위로 묶인다.
- **AC-07-9**: 할인액은 적용 전 금액을 초과하지 않으며, 최종 금액은 0원 미만이 되지 않는다.

> **[가정]** 한 주문에 동일 상품이 중복 포함되면 수량을 합산한다.
> **[가정]** 할인 계산의 원 단위 미만은 절사(floor)한다 — 정률 쿠폰에서 소수점이 나오면 버린다.

#### US-08: 내 주문 목록 조회
로그인 사용자가 기간을 지정해 자신의 주문 목록을 조회해, 과거 구매 내역을 확인할 수 있게 한다.

**상세 동작 규칙**
- **AC-08-1**: 조회 기간을 지정해 목록을 요청하면, 그 기간에 생성된 **본인 주문만** 최신순으로 보여준다.
- **AC-08-2**: 기간을 지정하지 않으면, 전체 기간의 주문을 보여준다.

#### US-09: 단일 주문 상세 조회
로그인 사용자가 특정 주문의 상세를 조회해, 무엇을 얼마에 샀는지 정확히 확인할 수 있게 한다.

**상세 동작 규칙**
- **AC-09-1**: 본인의 주문을 조회하면, 주문 항목별 이력(상품명·단가·수량), **적용 전 금액·할인액·최종 금액**, 주문 상태를 보여준다.
- **AC-09-2**: 다른 사용자의 주문을 조회하면, 요청을 거부한다.

### 4.4 브랜드 관리 (어드민)

#### US-10: 브랜드 등록
어드민이 새 브랜드를 등록해, 해당 브랜드의 상품을 판매할 수 있게 한다.

**상세 동작 규칙**
- **AC-10-1**: 필수 항목(브랜드명)을 갖춰 등록하면, 브랜드가 생성된다.
- **AC-10-2**: 필수값이 빠진 채 등록하면, 요청을 거부한다.

#### US-11: 브랜드 정보 수정
어드민이 기존 브랜드 정보를 수정해, 변경된 브랜드 정보를 반영할 수 있게 한다.

**상세 동작 규칙**
- **AC-11-1**: 존재하는 브랜드를 수정하면, 변경 내용이 반영된다.
- **AC-11-2**: 존재하지 않는 브랜드를 수정하면, 요청을 거부한다.

#### US-12: 브랜드 삭제
어드민이 브랜드를 삭제해, 더 이상 취급하지 않는 브랜드를 정리할 수 있게 한다.

**상세 동작 규칙**
- **AC-12-1**: 존재하는 브랜드를 삭제하면, **해당 브랜드의 모든 상품도 함께 삭제된다**.
- **AC-12-2**: 이미 생성된 주문은 이력으로 보존되므로, 브랜드·상품 삭제의 영향을 받지 않는다.
- **AC-12-3**: 브랜드·상품 삭제는 논리 삭제로 처리한다 — 데이터는 보존하되 조회·노출 대상에서 제외한다.

#### US-13: 브랜드 목록 / 상세 조회 (어드민)
어드민이 등록된 브랜드를 목록·상세로 조회해, 브랜드 현황을 관리할 수 있게 한다.

**상세 동작 규칙**
- **AC-13-1**: 어드민이 목록을 요청하면, 등록된 전체 브랜드 목록을 보여준다.

---

### 4.5 상품 관리 (어드민)

#### US-14: 상품 등록
어드민이 특정 브랜드에 상품을 등록해, 고객에게 판매할 수 있게 한다.

**상세 동작 규칙**
- **AC-14-1**: 필수 항목(상품명·가격·초기 재고)을 갖추고 **이미 등록된 브랜드**를 지정해 등록하면, 상품이 생성된다.
- **AC-14-2**: 존재하지 않는 브랜드에 상품을 등록하면, 요청을 거부한다.
- **AC-14-3**: 가격은 0 이상, 초기 재고는 0 이상의 정수여야 한다.

#### US-15: 상품 정보 수정
어드민이 상품 정보를 수정해, 가격·재고 등 변경 사항을 반영할 수 있게 한다.

**상세 동작 규칙**
- **AC-15-1**: 존재하는 상품을 수정하면, 변경 내용이 반영된다.
- **AC-15-2**: **상품의 브랜드는 수정할 수 없다.** 브랜드를 바꾸려는 요청은 거부한다.
- **AC-15-3**: 가격 수정은 **이후 주문부터** 적용되며, 기존 주문 이력에는 영향을 주지 않는다.
- **AC-15-4**: 재고 수정은 재고 수량을 **특정 값으로 설정**하는 것이다(증감이 아니라 절대 수량 반영).

#### US-16: 상품 삭제
어드민이 상품을 삭제해, 판매 종료된 상품을 정리할 수 있게 한다.

**상세 동작 규칙**
- **AC-16-1**: 존재하는 상품을 삭제하면, 고객 조회·주문 대상에서 제외된다.
- **AC-16-2**: 이미 주문에 포함된 상품은 이력 덕분에 주문 상세에 그대로 남는다.

#### US-17: 상품 목록 / 상세 조회 (어드민)
어드민이 등록된 상품을 브랜드별로 조회해, 재고를 관리할 수 있게 한다.

**상세 동작 규칙**
- **AC-17-1**: 어드민이 브랜드를 지정해 목록을 요청하면, 해당 브랜드 상품을 페이징하여 보여준다.

### 4.6 주문 조회 (어드민)

#### US-18: 주문 목록 / 상세 조회 (어드민)
어드민이 전체 주문을 목록·상세로 조회해, 운영 현황을 파악하고 문제를 추적할 수 있게 한다.

**상세 동작 규칙**
- **AC-18-1**: 어드민이 주문 목록을 요청하면, **모든 사용자의 주문**을 페이징하여 보여준다.
- **AC-18-2**: 어드민이 특정 주문을 조회하면, 주문자, 항목 이력, **적용 전 금액·할인액·최종 금액**, 주문 상태를 보여준다.

### 4.7 쿠폰 (대고객)

> 쿠폰은 **템플릿(원형)** 과 **발급된 내 쿠폰** 두 가지로 나뉜다. 어드민이 템플릿을 만들고(4.8), 사용자가 그 템플릿으로 자기 쿠폰을 발급받아 주문에 사용한다. 발급된 쿠폰은 **발급 시점의 혜택(할인 종류·값)·이름·만료일을 복사(스냅샷)해 보관**하므로, 이후 템플릿이 수정·삭제돼도 이미 발급된 쿠폰의 가치는 변하지 않는다(주문 이력의 상품명·단가 스냅샷과 같은 원칙).

#### US-19: 쿠폰 발급
로그인 사용자가 쿠폰 템플릿으로 자신의 쿠폰을 발급받아, 주문 시 할인에 사용할 수 있게 한다.

**상세 동작 규칙**
- **AC-19-1**: 존재하는(삭제되지 않은) 템플릿을 지정해 발급을 요청하면, 그 템플릿의 **할인 종류·할인 값·쿠폰명**과 **만료일(`발급 시각 + 유효일수`)** 을 복사한 사용 가능(`AVAILABLE`) 상태의 내 쿠폰이 생성된다.
- **AC-19-2**: **한 사용자는 같은 템플릿의 쿠폰을 1장만** 가질 수 있다(1인 1매). 이미 발급받은 템플릿을 다시 발급 요청하면 거부한다.
- **AC-19-3**: 존재하지 않거나 삭제된 템플릿으로 발급을 요청하면, "쿠폰을 찾을 수 없음"이라고 안내한다.
- **AC-19-4**: 로그인하지 않은 상태에서 발급을 요청하면, 요청을 거부한다.
- **AC-19-5 (경로 분리 · Round 7)**: 이 동기 발급은 **한도가 없는 무제한 템플릿 전용**이다. **한도가 걸린(선착순) 템플릿**은 이 경로로 발급하지 않고 **비동기 요청 경로(US-34)** 로만 발급한다 — 동기 경로가 선착순 한도를 우회하는 것을 막기 위해, 한도 있는 템플릿의 동기 발급 요청은 거부한다.

#### US-20: 내 쿠폰 목록 조회
로그인 사용자가 자신이 보유한 쿠폰을 조회해, 무엇을 언제까지 쓸 수 있는지 확인할 수 있게 한다.

**상세 동작 규칙**
- **AC-20-1**: 로그인 사용자가 본인 쿠폰 목록을 요청하면, 보유 쿠폰을 **쿠폰명·할인 내용·만료일·상태**와 함께 보여준다.
- **AC-20-2**: 쿠폰 상태는 **사용 가능(`AVAILABLE`) / 사용 완료(`USED`) / 만료(`EXPIRED`)** 로 구분해 보여준다. 만료는 별도로 저장하지 않고, "사용 가능 상태이지만 만료일이 지난" 쿠폰을 조회 시점에 만료로 판정한다.
- **AC-20-3**: 다른 사용자의 쿠폰 목록을 요청하면, 요청을 거부한다(타 유저 정보 직접 접근 불가).

### 4.8 쿠폰 관리 (어드민)

#### US-21: 쿠폰 템플릿 등록
어드민이 쿠폰 템플릿을 등록해, 사용자에게 발급할 쿠폰의 원형을 정의할 수 있게 한다.

**상세 동작 규칙**
- **AC-21-1**: 필수 항목(쿠폰명·할인 종류·할인 값·유효일수)을 갖춰 등록하면, 템플릿이 생성된다.
- **AC-21-2**: 할인 종류는 **정액(`FIXED`, 원 단위) / 정률(`RATE`, 퍼센트)** 두 가지다.
- **AC-21-3**: 정액 할인 값은 1 이상의 정수(원), 정률 할인 값은 1~100 사이의 정수(%)여야 한다. 유효일수는 1 이상의 정수여야 한다.
- **AC-21-4**: 정률 쿠폰에는 별도의 최대 할인 한도를 두지 않는다(비율만 적용).
- **AC-21-5**: **최소 주문 금액(min order amount)** 을 0 이상의 정수(원)로 둘 수 있다(선택, 기본 `0`=제한 없음). 주문 시 적용 전 금액이 이 값 미만이면 쿠폰을 사용할 수 없어 주문이 거부된다(AC-07-7). 이 조건은 발급 시점에 쿠폰으로 복사(스냅샷)되어, 이후 템플릿이 바뀌어도 이미 발급된 쿠폰의 조건은 변하지 않는다.

#### US-22: 쿠폰 템플릿 수정
어드민이 템플릿 정보를 수정해, 이후 발급될 쿠폰에 변경 사항을 반영할 수 있게 한다.

**상세 동작 규칙**
- **AC-22-1**: 존재하는 템플릿을 수정하면, 변경 내용이 반영된다.
- **AC-22-2**: 템플릿 수정은 **이후 발급되는 쿠폰부터** 적용되며, **이미 발급된 쿠폰(내 쿠폰)에는 영향을 주지 않는다**(발급 시점 스냅샷).
- **AC-22-3**: 존재하지 않는 템플릿을 수정하면, 요청을 거부한다.

#### US-23: 쿠폰 템플릿 삭제
어드민이 더 이상 발급하지 않을 템플릿을 삭제할 수 있게 한다.

**상세 동작 규칙**
- **AC-23-1**: 존재하는 템플릿을 삭제하면, 더 이상 발급 대상에서 제외된다(논리 삭제).
- **AC-23-2**: 템플릿 삭제는 **이미 발급된 쿠폰에는 영향을 주지 않는다** — 발급된 쿠폰은 스냅샷으로 자립하므로 만료 전까지 그대로 사용할 수 있다.

#### US-24: 쿠폰 템플릿 목록 / 상세 · 발급 내역 조회 (어드민)
어드민이 등록된 템플릿과 발급 현황을 조회해, 쿠폰 운영 상태를 파악할 수 있게 한다.

**상세 동작 규칙**
- **AC-24-1**: 어드민이 템플릿 목록을 요청하면, 등록된 템플릿을 페이징하여 보여준다.
- **AC-24-2**: 어드민이 특정 템플릿의 발급 내역을 요청하면, 그 템플릿으로 발급된 쿠폰(발급자·상태·만료일)을 페이징하여 보여준다.

### 4.9 결제 (대고객 · 외부 PG 연동) — Round 6

> 생성(`CREATED`)된 주문에 대해 외부 PG로 카드 결제를 진행한다. PG는 **비동기**라 요청 응답은 *접수 확인*일 뿐 결과가 아니며, 결과는 **콜백** 또는 **상태 조회**로 확정된다. 주문 생성(4.3)과 결제는 **별도 단계**다 — 주문 생성 시 재고 차감·쿠폰 사용이 끝나고, 결제는 그 주문(`orderId`)을 대상으로 한 번 이상 시도된다.
>
> **핵심 원칙**: ① **타임아웃은 실패가 아니라 "모름"** 이다(우리가 응답을 못 받아도 PG는 승인했을 수 있다) — 함부로 실패로 단정하지 않는다. ② 외부 호출의 부작용(승인)은 우리 트랜잭션으로 롤백되지 않는다. ③ 같은 요청이 두 번 도착하거나(더블클릭·재전송) 콜백이 두 번 와도(at-least-once) 결제는 한 번만 반영돼야 한다(멱등).

#### US-25: 결제 요청
로그인 사용자가 생성된 주문에 대해 카드로 결제를 요청해, 실제 구매를 완료할 수 있게 한다.

**정상 흐름 요약**: 결제 요청 수신(주문·카드) → 주문 행 비관락 + 소유·중복 확인 → 결제(`PENDING`) 저장·커밋(락 해제) → PG에 결제 요청(콜백 주소 포함) → 접수 확인(거래키) 저장. 결과 확정은 콜백/조회가 담당한다(US-27).

**상세 동작 규칙**
- **AC-25-1**: 결제는 **본인 소유의** `CREATED` 주문에만 요청할 수 있다. 타인 주문이거나 이미 결제 완료(`PAID`)된 주문이면 거부한다.
- **AC-25-2**: 결제 요청을 받으면 결제를 **`PENDING`(접수 대기)** 으로 먼저 저장하고, 그 다음 PG에 요청한다 — 이후 도착할 콜백·정산이 매칭할 대상이 항상 존재하게 한다. 결제 금액은 **요청 시점 주문 최종 금액의 스냅샷**으로 저장한다.
- **AC-25-3**: PG 요청의 **응답(접수 확인)은 결과가 아니다.** 접수되면 거래키(`transactionKey`)를 저장하되 결제는 **`PENDING` 그대로** 둔다. 성공/실패 확정은 콜백 또는 상태 조회로만 한다.
- **AC-25-4**: PG 요청이 **타임아웃되거나 PG 장애로 차단**되면, 결제를 실패로 단정하지 않고 **`PENDING` 으로 유지**한 채 "결제 접수됨(결과 대기)"으로 응답한다(타임아웃=모름). 이후 정산이 결과를 확인한다.
- **AC-25-5 (이중결제 차단 — 따닥)**: 같은 주문에 **살아있는 결제(`PENDING` 진행중 또는 `SUCCESS` 완료)** 가 있으면 새 요청을 거부한다(`CONFLICT`). 검사+저장을 **주문 행 비관락(`FOR UPDATE`)** 안에서 원자적으로 처리하므로, 동시 더블클릭이어도 한 건만 통과하고 PG는 1회만 호출된다(나머지는 거부, 청구 1회).
- **AC-25-6 (재결제)**: 결제가 실패(`FAILED`)해도 **주문은 `CREATED`로 유지**된다. `FAILED`는 "살아있는 시도"가 아니므로 AC-25-5의 차단을 통과하고, 사용자는 카드를 바꿔 같은 주문에 **다시 결제를 요청**할 수 있어 **새 결제(시도)** 가 생성된다 — 재고·쿠폰은 주문에 묶여 그대로이므로 다시 차감하지 않는다.

> **[설계]** 이중결제 차단은 클라이언트 멱등키가 아니라 **서버의 주문 행 비관락**으로 한다 — `orderId`가 이미 자연 키라 새 식별자/클라 계약이 불필요하고, 외부 청구가 트랜잭션 한가운데 있어 "호출 전 직렬화"가 필요하기 때문이다.
> **[범위]** 끝내 결제하지 않은 `CREATED` 주문의 정리(주문 취소·재고/쿠폰 복원)는 본 범위에서 제외한다(보상 트랜잭션 — 차기 과제).

#### US-26: 결제 상태 조회
사용자(브라우저)가 진행 중인 결제 상태를 조회해, 결과가 확정되면 완료 화면으로 넘어갈 수 있게 한다.

**상세 동작 규칙**
- **AC-26-1**: `paymentId`로 결제 상태(`PENDING`/`SUCCESS`/`FAILED`)와 실패 사유를 조회할 수 있다(우리 DB 기준, PG 재호출 없음 — `PENDING`이면 "처리중"으로 정직하게 노출). **본인 결제만** 조회 가능하다(소유권은 주문에서 도출, 타인 403·없으면 404).
- **AC-26-2**: PG 콜백은 우리 **서버**로 오므로 브라우저는 콜백을 직접 받을 수 없다 — 브라우저는 결과가 확정될 때까지 이 조회를 **폴링**해 `SUCCESS`/`FAILED`를 확인한다(콜백=서버 확정, 폴링=화면 갱신).

#### US-27: 결제 결과 확정 (콜백 수신 · 시스템)
PG가 처리 결과를 콜백으로 통지하면, 시스템이 결제·주문 상태를 확정한다.

**상세 동작 규칙**
- **AC-27-1**: 성공 콜백을 받으면 해당 결제를 `SUCCESS`로, **그 주문을 `PAID`** 로 전이한다. 실패 콜백(한도초과·잘못된 카드)이면 결제를 `FAILED`로 전이하고 사유를 기록한다(주문은 `CREATED` 유지).
- **AC-27-2 (멱등 — 콜백 중복)**: 같은 결제에 콜백이 여러 번 와도(at-least-once) **종결 상태(`SUCCESS`/`FAILED`)면 무시**한다(no-op). 상태 전이는 `PENDING`에서만 일어난다.
- **AC-27-3**: 콜백과 정산이 같은 결제를 동시에 종결시키려 해도 결과는 한 번만 반영된다(둘 중 하나만 전이 성공).
- **AC-27-4**: 콜백·조회 결과를 결제에 매칭하는 상관키는 거래키(`transactionKey`)뿐 아니라 **`orderId`로도 가능**해야 한다 — 요청 타임아웃으로 거래키 응답이 유실된 경우에도 결과를 붙일 수 있어야 하기 때문이다.

#### US-28: 결제 정산/복구 (운영 · 시스템)
콜백이 오지 않거나 요청이 PG에 닿지 못한 결제를, 시스템이 PG 상태 조회로 확인해 정합성을 맞춘다.

**상세 동작 규칙**
- **AC-28-1**: 일정 시간 이상 `PENDING`에 머문 결제는 PG **상태 조회 API**로 실제 결과를 확인해 `SUCCESS`/`FAILED`로 반영한다(콜백 유실 대비 안전망). 이미 종결된 결제는 건너뛴다(멱등).
- **AC-28-2**: PG에 **레코드가 없는**(요청이 접수되지 못한) `PENDING` 결제는 조회로 복구할 수 없다 — 일정 시간 경과 후 해당 시도를 만료/실패 처리해, 사용자가 새 시도로 재결제할 수 있게 한다.

### 4.10 이벤트 기반 집계·전파 (시스템 · 내부 이벤트 / Kafka) — Round 7

> 좋아요·주문·결제·조회처럼 **이미 확정된 사실**에서 파생되는 부가 효과(지표 집계·알림·행동 로깅)를 주요 거래 흐름에서 분리한다. 주요 흐름(재고·결제 등 실패 시 사실 자체가 무효여야 하는 것)은 지금처럼 동기·인-트랜잭션으로 두고, 부가 효과는 **이벤트**로 뒤로 뺀다. 한 애플리케이션 안의 분리는 스프링 `ApplicationEvent`(Step 1)로, **시스템 간** 전파는 **Kafka**(Step 2)로 하며, 집계 결과(`product_metrics`)는 별도 앱(`commerce-streamer`)이 소유한다. 마지막으로 **선착순 쿠폰 발급**(Step 3)은 Kafka를 전파가 아니라 폭주하는 요청을 순차화하는 **실행 경로**로 써서, 소비자(`commerce-streamer`)가 **조건부 원자 UPDATE**로 한도까지만 발급한다(US-34).
>
> **핵심 원칙**: ① 부가 효과의 실패가 **주요 성공을 되돌리지 못한다**. ② **커밋된 사실은 반드시 전파된다**(전파 유실 금지). ③ 같은 사실이 재전달돼도 **한 번만 반영된다**(멱등). ④ 못 처리하는 메시지가 **파이프라인을 막지 못한다**(실패 격리). — 결제(4.9)의 "타임아웃=모름·멱등" 원칙을 시스템 간 비동기 전파로 확장한 것이다.

#### US-29: 부가 효과의 이벤트 분리 (Step 1)
서비스가 주요 거래(좋아요·주문·결제)의 부가 효과(알림·로깅·집계)를 주요 흐름에서 떼어내, 부가 로직의 실패·지연이 거래를 방해하지 않게 한다.

**상세 동작 규칙**
- **AC-29-1**: 좋아요 등록/취소, 주문 생성, 결제 성공, 상품 상세 조회가 일어나면 각각 도메인 이벤트를 발행한다.
- **AC-29-2**: 알림·행동 로깅 같은 부가 리스너는 **발행 트랜잭션이 커밋된 뒤에만** 실행된다(커밋 후 처리). 롤백된 행동은 부가 효과도 남기지 않는다(유령 반영 방지).
- **AC-29-3**: 부가 리스너의 실패는 **주요 흐름의 성공을 되돌리지 못한다**(집계 실패 ≠ 좋아요 실패).
- **AC-29-4 (하이브리드)**: 정렬/표시에 쓰이는 좋아요 수(`products.like_count`)는 좋아요 트랜잭션이 **커밋된 뒤 비동기(`@Async` AFTER_COMMIT)** 로 원자 UPDATE된다 — 좋아요 등록/취소 **자체는 즉시 성공**하고 카운터는 **eventual·best-effort**로 뒤따른다(비동기 큐가 크래시하면 그 증분은 유실되고 재시도가 없어 드리프트 가능). 정렬은 작은 랙·드리프트를 허용한다. **유실 없는 수렴**(재시도·내구성)은 별도 앱의 지표 집계(`product_metrics`, US-30)가 백스톱한다 — 같은 이벤트를 두 소비자가 듣되 하나는 **빠른 로컬 best-effort**, 하나는 **느린 크로스앱 guaranteed**다. 좋아요 성공과 집계를 한 트랜잭션에 묶지 않은 건 커넥션을 두 개 점유하는 압박(실측 실패)을 피하기 위함이다.

#### US-30: 상품 지표 집계 — 좋아요 · 판매량 · 조회수 (Step 2)
시스템이 상품별 좋아요·판매량·조회수를 별도 집계 저장소에 모아, 분석/대시보드가 조회 경로에 부담을 주지 않고 지표를 읽을 수 있게 한다.

**상세 동작 규칙**
- **AC-30-1**: 좋아요 등록/취소가 확정되면 그 상품의 **좋아요 수** 집계가 증가/감소한다(집계는 음수가 되지 않는다).
- **AC-30-2**: 결제가 **성공**하면 그 주문의 **상품별 판매 수량만큼 판매량**이 누적된다 — 판매량은 "주문 생성"이 아니라 "결제 성공" 기준이다(주문했다 미결제한 건은 팔린 게 아니다).
- **AC-30-3**: 상품 상세가 조회되면 **조회수**가 증가한다. 조회수는 **유실을 허용하는 분석 지표**다(몇 건 누락돼도 서비스에 지장이 없다).
- **AC-30-4**: 지표 집계는 주문/좋아요/조회 응답을 **지연시키지 않는다**(비동기, eventual). 집계가 실패해도 거래는 되돌아가지 않는다.
- **AC-30-5**: 지표 저장소는 조회 경로의 좋아요 수(`products.like_count`, 정렬용·로컬 best-effort)와 **물리적으로 분리된 별도 read model**이다 — 소비처와 **보장 수준**이 다르므로 의도적으로 중복한다(빠른 로컬 best-effort 카운터 vs 느린 크로스앱 guaranteed 집계; **둘 다 eventual**이되 후자만 유실 없는 수렴을 보장).

#### US-31: 전파 유실 방지 — Transactional Outbox (Step 2)
시스템이 상태 변경과 그 전파를 원자적으로 묶어, 커밋된 사실이 전파 도중 유실되지 않게 한다.

**상세 동작 규칙**
- **AC-31-1**: 상태 변경과 **전파 기록(outbox)** 은 하나의 트랜잭션으로 묶인다 — 변경이 커밋되면 전파 기록도 반드시 남고, 롤백되면 전파 기록도 없다(DB 커밋과 메시지 발행을 동시에 원자적으로 못 묶는 dual-write 문제를 DB 로컬 트랜잭션으로 환원).
- **AC-31-2**: 전파 발행(Kafka)이 실패해도 기록은 남아 **재시도로 반드시 발행된다**(at-least-once). 커밋된 비즈니스 사실은 포기하지 않는다(브로커 장애가 복구되면 자연히 발행).
- **AC-31-3**: **조회수처럼 상태 변경이 없고(읽기) 유실을 허용하는** 신호는 outbox를 거치지 않고 **직접 발행**할 수 있다 — outbox의 존재 이유(상태변경과 전파의 원자성)에 묶을 대상이 없으므로, 내구성 대신 성능을 택한다.

#### US-32: 소비자 멱등 — effectively-once (Step 2)
시스템이 같은 이벤트를 여러 번 전달받아도 집계를 한 번만 반영한다.

**상세 동작 규칙**
- **AC-32-1**: 같은 이벤트가 재전달돼도(at-least-once) 집계는 **한 번만** 반영된다(중복 증가 없음).
- **AC-32-2**: **멱등 판정과 집계 갱신은 하나의 트랜잭션**으로 묶인다 — "집계만 되고 처리 기록 누락" 또는 "기록만 되고 집계 누락"이 생기지 않는다.
- **AC-32-3**: 멱등 스코프는 **소비자(handler)별로 분리**된다 — 같은 이벤트를 서로 다른 소비자가 각각 한 번씩 독립적으로 처리할 수 있어야 한다.

#### US-33: 실패 격리 — Dead Letter Queue (Step 2)
시스템이 처리할 수 없는 메시지를 격리해, 한 건의 실패가 전체 소비를 멈추지 않게 한다.

**상세 동작 규칙**
- **AC-33-1**: 처리에 실패한 메시지는 정해진 횟수 재시도 후 **격리 저장소(DLQ)** 로 옮겨지고, **뒤 메시지 처리는 계속**된다(poison 메시지가 파티션을 영구 정지시키지 않는다).
- **AC-33-2**: **일시 장애**(DB 순단·외부 API 타임아웃 등)는 재시도로 흡수하고, **결정적 실패**(필수값 누락·역직렬화 불가 등)는 재시도 없이 즉시 격리한다(재시도해도 반드시 실패하므로).
- **AC-33-3**: 격리된 메시지는 **원문과 실패 원인**(원본 토픽/파티션/오프셋·예외 클래스·메시지)을 함께 보관해, 운영자가 원인을 확인하고 재처리할 수 있게 한다(DLQ는 버리는 곳이 아니라 보관·재처리소다).

#### US-34: 선착순 쿠폰 발급 (Step 3)
로그인 사용자가 수량이 한정된(선착순) 쿠폰 템플릿에 발급을 요청하면, 시스템이 요청을 접수하고 비동기로 순차 처리해 **한도까지만** 발급하고, 사용자가 그 결과를 확인할 수 있게 한다.

> 무제한 발급(US-19)은 경합이 없어 동기로 즉시 끝낼 수 있지만, **한도가 걸린 발급은 "누가 마지막 한 장을 가져가느냐"가 곧 동시성 문제**다. 요청을 Kafka에 넣고 `templateId`를 키로 삼아 **한 템플릿의 요청이 한 파티션 → 단일 소비자**로 순차 처리되게 한 뒤, 발급 슬롯은 **조건부 원자 UPDATE**(`issued_count + 1 WHERE issued_count < issue_limit`, 영향 행 수로 판정)로 확보한다 — 재고 차감과 같은 패턴이라 락 없이 초과 발급이 불가능하다(파티션 직렬화는 순서·멱등을 돕고, 한도 자체는 원자 UPDATE가 보장).
>
> 소비자는 **`commerce-streamer`가 호스팅**한다(Kafka consumer 앱이 실제로 처리). streamer 는 쿠폰 도메인을 복제하지 않고, 발급이 필요로 하는 최소 쿼리만 **JdbcTemplate 으로 같은 MySQL(shared DB)** 에 실행한다. 대가는 발급 규칙(스냅샷 복사·만료 계산·한도 검사)이 SQL 로 재표현되어 `commerce-api` 의 `UserCoupon.issue()`/`CouponTemplate` 불변식과 **드리프트**할 수 있다는 것(컴파일러가 잡아주지 않음) — 규칙이 작고 잘 바뀌지 않아 감수한 선택이다. Kafka 는 실행 경로(요청 버퍼링·직렬화)를 제공한다.

**상세 동작 규칙**
- **AC-34-1 (요청 접수)**: 한도가 있는(선착순) 템플릿에 발급을 요청하면, 요청을 **`PENDING`(접수)** 으로 저장하고 즉시 **`requestId`** 를 반환한다(실제 발급은 비동기). 요청 기록과 전파(outbox)는 **한 트랜잭션**으로 묶는다(US-31과 같은 원자성).
- **AC-34-2 (경로 분리)**: **무제한 템플릿은 동기 발급(US-19)**, **한도 있는 템플릿은 이 비동기 요청 경로**로만 발급한다. 동기 경로는 한도 있는 템플릿을 **거부**한다(동기 경로로 한도를 우회하는 뒷문 차단).
- **AC-34-3 (선착순 수량 제한)**: 소비자는 발급 슬롯을 **조건부 원자 UPDATE**(`issued_count = issued_count + 1 WHERE issued_count < issue_limit`)로 확보하고, 확보 실패(영향 행 0 = 한도 소진)면 요청을 **`SOLD_OUT`** 으로 확정한다 — 동시 요청이 몰려도 **초과 발급이 발생하지 않는다**(재고 차감과 같은 원자 UPDATE 패턴, 락 불필요).
- **AC-34-4 (중복 방지 · 1인 1매)**: 이미 그 템플릿을 발급받은 유저의 요청은 **슬롯을 소모하지 않고 `ALREADY_ISSUED`** 로 확정한다(AC-19-2를 비동기 경로로 확장). `user_coupons`의 `(user_id, template_id)` 유니크가 최후 방어선이다.
- **AC-34-5 (멱등)**: 같은 요청이 재전달돼도(at-least-once) **두 번 발급하지 않는다** — 요청 상태가 `PENDING`일 때만 처리하고 이미 종결된 요청은 무시한다(요청 상태 원장이 소비자 멱등 키를 겸한다). 소비자는 처리 대상(`userId`·`templateId`)을 외부 경계인 메시지가 아니라 **DB 요청 행**을 진실로 삼아, 요청 행과 발급 결과가 갈리는 것을 막는다.
- **AC-34-6 (결과 확인 · 폴링)**: 클라이언트는 `requestId`로 처리 상태(`PENDING`/`SUCCESS`/`SOLD_OUT`/`ALREADY_ISSUED`/`FAILED`)를 조회한다. **본인 요청만** 조회할 수 있다(타인 `requestId`는 존재를 노출하지 않고 "없음"으로 응답).
- **AC-34-7 (결정적 실패 vs 재시도)**: **재시도해도 성공할 수 없는 실패**(템플릿 삭제·선착순 대상 아님)만 `FAILED`로 확정하고, **일시 장애**(DB 순단 등)는 상태를 바꾸지 않고 재시도→DLQ로 격리한다(US-33 렌즈). `FAILED`는 "재시도 무의미"만 의미하며, 복구 가능한 실패는 상태로 남기지 않는다.

### 4.11 주문 대기열 (대고객 · 시스템) — Round 8

> 블랙 프라이데이급 트래픽(평시 100 → 피크 10,000 TPS)에서 주문 API 하류(DB 커넥션 풀 40개·재고 핫로우 비관락)를 보호하는 **back-pressure** 장치다. 스케일아웃이 답이 아닌 영역 — DB·핫로우 직렬화 지점은 서버를 늘려도 그대로다 — 이므로, 용량 확장 대신 **하류가 감당할 속도로 상류 유입을 조절**한다. 유저는 대기열 진입 → 순번 폴링 → 입장 토큰 수신 → 토큰으로 주문 흐름을 타며, 주문 API 내부와 이후 흐름(R7 이벤트 파이프라인)은 무변경이다.
>
> **핵심 원칙**: ① 먼저 온 유저가 먼저 처리된다(공정성 — 재시도 운에 맡기는 429 거부와 달리). ② 대기 중인 유저에게 순번·예상 대기 시간을 제공해 이탈과 재시도 폭풍을 막는다. ③ 발급 속도가 곧 주문 유입 TPS 다 — 하류에서 가장 좁은 병목의 용량에서 역산한다. ④ 대기열은 행사 때만 켜는 장치다(`queue.enabled` 토글, 평시·테스트 환경은 기존 주문 흐름 그대로).

#### US-35: 대기열 진입
로그인 사용자가 주문 대기열에 진입해, 폭증 트래픽 속에서도 순서를 보장받고 주문할 수 있게 한다.

**상세 동작 규칙**
- **AC-35-1**: 로그인 사용자가 진입을 요청하면 대기열에 등록되고, 순번(1부터 시작)·예상 대기 시간·다음 폴링 간격을 응답한다.
- **AC-35-2 (멱등)**: 이미 대기 중인 사용자가 재진입해도 **최초 진입 시각이 보존되어 순번이 유지**된다 — 대기 화면의 새로고침이 곧 재진입이므로, 재진입이 줄 맨 뒤로 보내면 안 된다(Redis `ZADD NX`).
- **AC-35-3**: 이미 입장 토큰을 받은 사용자가 진입을 요청하면 **다시 줄 세우지 않고 토큰을 반환**한다 — 재줄세우기는 토큰 TTL 만 태우며 줄을 두 번 서게 한다.
- **AC-35-4**: 로그인하지 않은 상태의 진입 요청은 거부한다.

#### US-36: 순번 조회 (폴링)
대기 중인 사용자가 자신의 순번과 예상 대기 시간을 조회해, 기다리는 동안 이탈하지 않게 한다.

**상세 동작 규칙**
- **AC-36-1**: 대기 중이면 순번(1-based)·예상 대기 시간(≈ 순번 ÷ 발급 속도, 추정값이므로 "약 N초"로 표기)·다음 폴링 간격(`pollAfterMillis`)·전체 대기 인원(`ZCARD`, "N명이 함께 대기 중" 사회적 증거로 이탈 완화)을 응답한다.
- **AC-36-2 (동적 폴링 주기)**: 폴링 간격은 순번 구간별로 다르다 — 앞순번일수록 짧게(토큰 수신 인지 지연 최소화), 뒷순번일수록 길게(의미 없는 조회 억제). **다음 폴링 시점의 제어권은 서버가 갖는다**(응답 필드) — 클라이언트에 주기를 하드코딩하면 부하가 문제 될 때 손쓸 방법이 배포뿐이다.
- **AC-36-3**: 입장 토큰이 발급된 사용자에게는 `position=0` 과 함께 **토큰을 응답**한다.
- **AC-36-4**: 대기열에 없는 사용자(미진입·토큰 만료 후)의 조회는 "대기열에 없음"으로 안내해 재진입을 유도한다 — 이탈 유저가 "곧 될 것 같은 대기"로 오인하고 폴링을 계속하지 않게 명시적으로 끊는다.

#### US-37: 입장 토큰 발급·검증 (시스템 · 주문 게이트)
시스템이 하류가 감당할 속도로만 입장 토큰을 발급하고, 주문 API 가 토큰을 검증·소진해 유입 총량을 강제한다.

**상세 동작 규칙**
- **AC-37-1 (순차 발급)**: 스케줄러가 일정 주기마다 대기열 앞에서 배치 크기만큼 꺼내(원자적 `ZPOPMIN`) TTL 있는 입장 토큰을 발급한다. 발급 속도(주기·배치 크기)는 하류 병목에서 역산한 **런타임 설정값**이다(행사 상품 구성에 따라 재산정).
- **AC-37-2 (분산 발급)**: 같은 발급 총량이라도 1초 일괄이 아니라 **짧은 주기(100ms)로 쪼개** 발급한다 — 일괄 발급은 Thundering Herd 로 매초 하류 스파이크를 재현한다(실측: 단일 핫로우 기준 주문 p50 이 11배 악화).
- **AC-37-3 (주문 게이트)**: 대기열이 켜진 동안 주문 생성 요청은 유효한 입장 토큰(`X-Entry-Token` 헤더)이 필수다. 토큰 부재·불일치·만료는 **403** 으로 거부한다 — "인증은 됐지만 입장 권한 없음" 시맨틱(401 인증 실패·429 rate limit 과 구분). 토큰 헤더가 아예 없으면 **인증 조회 전에 즉시 거부**한다(DB 를 보호하려는 관문이 무자격 요청에 인증 쿼리를 써 주면 모순).
- **AC-37-4 (토큰 소진)**: 토큰은 주문 **성공(2xx)에만 소진**된다. 실패(재고 부족·입력 오류)한 유저의 토큰은 보존되어 TTL 내 재시도할 수 있다 — 시스템 사정으로 줄을 다시 서게 하지 않는다.
- **AC-37-5 (동시 주문 차단)**: 같은 토큰으로 동시에 들어온 주문은 **유저당 1건만** 통과하고 나머지는 **409** 로 거부한다. 토큰 검증(find+대조)은 아무것도 소진하지 않고 소진이 완료 후(AC-37-4)라, 검증 통과 직후 유저당 in-flight 마크를 `SETNX`(`processing-token:{userId}`) 로 선점해 그 창을 닫는다 — 마크 없이는 토큰 1장으로 N건이 통과해 "발급 속도 = 유입 TPS"(핵심 원칙 ③)가 깨진다. 마크는 완료 시 해제하며, **선점한 요청만** 해제·소진하고(거절된 동시 요청이 선행 요청의 마크·토큰을 지우지 않도록), 마크 TTL 은 크래시로 해제가 누락됐을 때의 자동 해제 안전망이다. 마크 값은 **요청마다 고유한 owner token** 이고 해제는 그 값이 일치할 때만 삭제한다(compare-and-delete, Lua 원자 실행) — TTL 만료 후 다른 요청이 새로 선점한 마크를 늦게 도착한 해제가 지우지 않도록.
- **AC-37-6 (토글)**: `queue.enabled=false` 면 주문은 토큰 없이 기존과 동일하게 동작한다(평시·테스트 환경 무손상).
- **AC-37-7 (유실 자가 복구)**: 꺼내기(pop)와 토큰 저장 사이는 원자적이지 않다 — 그 찰나(수 ms)에 장애가 나면 해당 유저는 토큰 없이 대기열에서 빠지지만, **재진입으로 자가 복구**된다(US-36 AC-36-4 의 재진입 안내가 복구 경로).

### 4.12 일간 상품 랭킹 (대고객 · 시스템) — Round 9

> R7 파이프라인이 수집하는 유저 행동 이벤트(조회·좋아요·주문)로 **일간 상품 랭킹**을 만들어 Top-N 목록과 개별 순위를 제공한다.
>
> **데이터 흐름**: collector(전용 컨슈머 그룹)가 신호별 raw 보드 4개(`ranking:{view|like|order_count|order_qty}:{yyyyMMdd}`)에 가중치 없는 카운트를 실시간 적재하고(Collect), 합성 스케줄러가 주기적으로 raw × 가중치를 `ZUNIONSTORE` 로 합산해 서빙 보드(`ranking:all:{yyyyMMdd}`)를 재생성하며(Score), API 는 서빙 보드만 읽는다(Serving). **가중치는 저장 시점이 아니라 합성 시점에 적용되므로** 설정 변경이 당일 전체에 소급 적용되고, 신호별 보드 자체가 "이 순위를 만든 게 무엇인지"를 분해해 볼 수 있는 관측 데이터가 된다.

#### US-38: 랭킹 신호 수집 (시스템)
시스템이 유저 행동 이벤트를 신호별 raw 보드에 유실 없이 적재한다.

**상세 동작 규칙**
- **AC-38-1 (전용 컨슈머 그룹)**: 랭킹 collector 는 metrics collector 와 **다른 컨슈머 그룹**으로 같은 토픽을 소비한다 — offset·실패·재시도가 독립되어, Redis 장애 시 랭킹 그룹만 정지(랙 = 무손실 버퍼)하고 metrics 는 무영향이며 복구 후 랙을 따라잡아 유실이 없다.
- **AC-38-2 (신호 적재)**: 조회 +1(view) / 좋아요 +1·취소 **−1**(like) / 주문 건수 +1(order_count)·수량 +N(order_qty)을 각 보드에 `ZINCRBY` 한다. 건수와 수량은 상호 유도 불가능한 정보라 분리 보존한다 — raw 에서 버린 정보는 소급 복구할 수 없다.
- **AC-38-3 (버킷 귀속)**: 이벤트는 처리 시각이 아닌 **발생 시각(occurredAt, KST)** 의 날짜 보드에 귀속된다 — 자정 직후 도착한 전일 이벤트는 전일 보드로 간다(보존 TTL 2일이 이를 뒷받침).
- **AC-38-4 (음수 허용)**: 취소 반영으로 점수가 0 미만이 될 수 있고 보정하지 않는다 — 취소 감점은 "좋아요→취소 반복"으로 점수를 쌓는 어뷰징을 수학적으로 봉쇄하는 유일한 정책이고, 음수 점수는 그 정책이 남기는 자연스러운 결과다(최하위로 가라앉아 Top-N 에 나타나지 않음).
- **AC-38-5 (멱등 없음 = 의도)**: 중복 전달의 이중 가산은 근사 지표 예산으로 수용한다. 대가로 랭킹 경로는 DB 무의존 순수 프로젝션이 되고, **컨슈머 그룹 offset 리셋만으로 보드 재구축**이 가능하다(멱등 원장은 중복 방지 장치인 동시에 재생 차단 장치다).
- **AC-38-6 (실패 분류)**: 일시 장애(Redis 연결·타임아웃)는 **무한 재시도**(offset 미커밋), 그 외(poison)는 로그 후 **skip** 한다 — 기다리면 낫는 실패와 기다려도 안 낫는 실패의 이분법. 랭킹 그룹의 DLT 격리는 두지 않는다(같은 메시지를 metrics 그룹이 이미 DLT 보존).

#### US-39: 점수 합성 (시스템)
시스템이 raw 신호를 가중 합산해 서빙 보드를 만들고, 날짜 전환 시 콜드 스타트를 완화한다.

**상세 동작 규칙**
- **AC-39-1 (주기 합성)**: 합성은 서빙 보드를 **덮어쓰는 전체 재계산**이라 멱등이며 다중 인스턴스 동시 실행에 무해하다. 서빙 신선도 = 합성 주기(기본 60초, 설정값). 전일 보드도 함께 재합성해 지연 도착 이벤트를 반영한다.
- **AC-39-2 (가중치 외부화)**: 가중치(기본 view 0.1 / like 0.2 / order_count 0.7 / order_qty 0)는 설정값이며, 변경은 다음 합성부터 **당일 전체에 소급**된다. 값 자체의 튜닝은 스코프 밖(A/B·ML 영역).
- **AC-39-3 (carry-over)**: **23:50 에 당일 raw 점수 × 계수(기본 0.1)를 익일 raw 보드에 사전 시드**하고 즉시 익일 서빙 보드를 합성한다 — 자정에 조회 키가 전환되는 순간 보드가 이미 존재해 콜드 스타트 창이 없다(전환 경계와 시드 시점의 레이스 제거). 비용은 시드 스냅샷이 23:50 시점이라 마지막 10분 활동이 이월에서 빠지는 것으로, 0.1 계수가 걸린 시드에서는 허용 오차 안이다. 시드는 대상 보드의 **기존 누적분을 보존**하는 합산이어야 하고, 재실행·다중 인스턴스는 **SETNX 마커**로 1회 실행을 보장한다.
- **AC-39-4 (키·TTL)**: 일별 키 분리 + TTL 2일(집계 윈도우의 2배). 원본 이벤트가 상류(Kafka·RDB)에 있고 데이터 수명이 하루라, 보드가 유실돼도 영향은 최대 1일로 제한된다.

#### US-40: 랭킹 조회 (대고객)
사용자가 일간 랭킹과 개별 상품의 순위를 조회한다.

**상세 동작 규칙**
- **AC-40-1 (페이지 조회)**: `GET /api/v1/rankings?date&page&size` — 점수 내림차순으로, 상품 ID 가 아닌 **상품 정보(이름·브랜드·가격·좋아요 수)가 조립**되어 반환된다. size 상한 100(보드 전체 스캔 방지). date(yyyyMMdd) 생략 시 오늘, 이전 날짜는 TTL 내에서 조회 가능하다.
- **AC-40-2 (삭제 상품 제외)**: soft-delete 된 상품은 응답에서 제외하되 **순위 gap 은 유지**한다 — 재번호를 매기면 같은 상품의 순위가 페이지 조회와 단건 조회에서 어긋난다. 따라서 페이지가 size 미만일 수 있다.
- **AC-40-3 (상세 통합)**: 상품 상세 응답에 오늘 순위(rank)가 포함되며, **순위에 없다면 null** 이다("오늘 이벤트 없음"은 오류가 아니라 상태). 순위 조회 실패도 null 로 흡수한다 — 부가 정보의 실패가 본 응답(상품 상세)까지 실패시키면 안 되기 때문이다(실패를 그대로 노출하는 랭킹 API 와 대비되는 지점).

## 5. 비기능 요구사항

- **보안/권한**: **본인 데이터 접근 경계**(주문/좋아요/쿠폰 목록)는 명세상 강제한다.
- **정합성**: 주문 생성 시 재고 차감·쿠폰 사용 처리·주문 저장은 하나의 트랜잭션으로 묶여 전부 성공하거나 전부 취소된다(AC-07-4·AC-07-8).
- **동시성(재고)**: 동일 상품에 대한 동시 주문에서도 **초과 판매(oversell)가 발생하지 않는다** — 주문 시 대상 상품 행을 **비관적 쓰기 락**(`@Lock(PESSIMISTIC_WRITE)`, 스냅샷용 조회에 락을 얹음)으로 잠근 뒤 도메인이 `재고 ≥ 수량` 검증 후 차감해 보장한다(AC-07-2·AC-07-3). 동시 주문이 같은 행 락에 직렬화되어 read-modify-write 간극이 사라지므로 lost update가 차단된다.
- **동시성(쿠폰)**: 한 쿠폰이 동시에 두 주문에 **중복 사용**되지 않는다 — `user_coupons`에 **낙관적 락(`@Version`)** 을 두어, `AVAILABLE→USED` 전이가 동시에 일어나면 한쪽만 성공하고 나머지는 충돌로 주문 트랜잭션 전체가 롤백된다(AC-07-8). 한 유저·한 쿠폰의 저경합이라 무는 비용이 거의 없는 낙관적 락을 택했고, 어차피 로드하는 행에 락을 얹는 재고(비관적 락)와 기법을 달리한다.
- **동시성(좋아요 수)**: 동일 상품에 여러 명이 동시에 좋아요/취소해도 **좋아요 수가 정확히 반영된다** — 좋아요 수를 `products.like_count`로 비정규화하고, 행이 실제로 INSERT/DELETE 됐을 때만(영향 행 수 == 1) **원자적 UPDATE**(`like_count ± 1`)로 증감한다. 인기 상품에 몰리는 고경합 단순 카운터라 비관 락(보유 길어짐)·낙관 락(재시도 폭증) 모두 부적합해 원자 UPDATE를 택했다 — 재고(비관 락)·쿠폰(낙관 락)과 또 다른 결이다. **(Round 7)** 이 원자 UPDATE는 좋아요 트랜잭션 **안이 아니라 커밋 후 `@Async` 리스너**에서 수행된다(US-29·4.10) — 원자성/기법 선택 자체는 그대로지만, 좋아요 성공과 집계를 분리한 대가로 카운터는 **eventual·best-effort**(비동기 유실 시 드리프트, 재시도 없음)가 됐다. 유실 없는 수렴은 `product_metrics`가 맡는다.

### 외부 연동(PG) 정합성·회복 (Round 6)

내부 DB는 트랜잭션으로 정합성을 보장하지만 **PG는 그 트랜잭션 밖**에 있다. 아래는 외부 연동에서 충분히 오래 돌리면 반드시 일어나는 일들에 대한 요구다.

- **트랜잭션 경계(dual-write)**: PG 호출은 **트랜잭션 밖**에서 한다 — 외부 응답 시간만큼 DB 커넥션·락을 점유하면 풀이 고갈되기 때문이다. 결제(`PENDING`)를 **먼저 커밋한 뒤** PG를 호출해, 콜백/정산이 매칭할 대상이 항상 존재하게 한다(AC-25-2).
- **자원 보호(Resilience)**: PG 호출에 **타임아웃**을 둔다 — 요청 타임아웃은 *접수 확인*까지만 짧게 잡고, *처리 지연*은 타임아웃 대상이 아니라 콜백/정산으로 기다린다. 반복 실패·느린 응답이 누적되면 **Circuit Breaker**로 호출을 차단해 장애가 내부로 전파되지 않게 하고, 차단/타임아웃 시 **Fallback**으로 사용자에겐 결제를 실패가 아니라 **`PENDING`(접수·대기)** 으로 응답한다(AC-25-4). PG 재시도(`Retry`)는 멱등이 보장될 때만 backoff와 함께 적용한다.
- **상태 정합성(내부↔PG)**: 내부 결제 상태(`PENDING`/`SUCCESS`/`FAILED`)와 PG 실제 상태가 어긋날 수 있는 조합(콜백 유실, 요청 타임아웃, 미접수, 콜백 중복)을 인지하고, 각 어긋남을 **콜백 또는 정산**이 정정한다. "타임아웃→실패" 단정을 하지 않으면 (내부=실패, PG=승인)이라는 돈 사고 조합이 구조적으로 차단된다.
- **멱등성/이중결제 차단**: 요청 중복(따닥)은 **주문 행 비관락(`FOR UPDATE`) + "살아있는 시도(PENDING·SUCCESS) 차단"** 으로 막아 PG 청구를 1회로 직렬화한다(AC-25-5). 콜백 중복은 **종결 상태 no-op 전이 가드**로 흡수하고(AC-27-2), 콜백·정산의 동시 종결은 같은 가드가 값-멱등으로 흡수해 전이가 실제 일어났을 때만 주문을 `PAID`로 반영한다(AC-27-3) — 지금은 무해해 별도 락이 없으나 `PAID`에 부작용이 붙으면 낙관락(`@Version`)을 도입한다(현재 미적용).
- **회복(Reconciliation)**: 콜백만 신뢰하면 유실 시 영구 `PENDING`이 되므로, **PG 상태 조회**를 콜백과 이중화한다(주기적 정산 + 수동 복구). 접수되지 못한(PG에 레코드 없는) 결제는 조회로 복구되지 않으므로 만료/재시도로 분기한다(AC-28-1·AC-28-2).

### 이벤트 기반 아키텍처 정합성 (Round 7)

내부 트랜잭션의 강한 정합성을 포기하는 대신 **결과적 정합성(eventual consistency)** 과 **가용성/확장성**을 얻는 영역이다. 아래는 비동기 전파를 충분히 오래 돌리면 반드시 일어나는 일들에 대한 요구다.

- **경계 분리(주요 vs 부가)**: "실패 시 비즈니스 사실 자체가 무효여야 하면 **주요**(동기·인-트랜잭션), 아니면 **부가**(이벤트)." 재고 차감·결제 확정은 주요라 종전대로 두고, 알림·로깅·지표 집계는 부가라 이벤트로 뺀다. 부가 리스너는 **커밋 후**에 듣고, 그 실패가 주요 트랜잭션을 되돌리지 못한다(US-29).
- **전달 보장 사슬(effectively-once)**: producer→broker 는 idempotence로 구간 중복을 제거하고, **outbox**로 발행 유실을 0으로 만든다(AC-31). broker→consumer 는 at-least-once라 재전달이 정상이며, **소비자 멱등 원장**이 중복을 흡수해 최종적으로 정확히 한 번 반영한다(AC-32). "어디서도 유실 없음 + 중복은 흡수"의 조합이 exactly-once의 실용적 대체다.
- **순서 보장(파티션 직렬화)**: Kafka는 **파티션 내부(=키 단위)** 에서만 순서를 보장한다. 전파 키를 `aggregateId`(예: `productId`)로 두면 같은 애그리거트의 이벤트는 항상 같은 파티션 → **단일 소비자 스레드가 순차 처리** → 집계의 read-modify-write에 락이 필요 없다(파티션 직렬화가 곧 동시성 제어). 대가는 처리량이 파티션 수에 묶이는 것. **선착순 쿠폰 발급(US-34)** 도 키를 `templateId`로 두어 요청을 순차화하지만, 한도 강제는 파티션 직렬화가 아니라 **조건부 원자 UPDATE**(`issued_count < issue_limit`)가 맡는다 — 재고 차감과 같은 결이라 파티션 가정이 흔들려도 초과 발급이 없다(재고=비관락, 쿠폰 사용=낙관락, 좋아요 수·선착순 발급=조건부 원자 UPDATE, 지표 집계=파티션 직렬화 — 경합 성격에 따라 달리 택한 동시성 기법들).
- **다중 writer read model**: 서로 다른 이벤트 스트림(좋아요/조회 vs 판매)이 같은 지표 행의 **다른 컬럼**을 갱신하면, 각 카운터는 파티션 직렬화로 단일 writer지만 행 전체로는 다중 writer다. **컬럼 단위 갱신**(변경된 컬럼만 UPDATE)으로 서로의 컬럼을 덮어쓰지 않게 해 교차 lost update를 막는다(`@Version` 낙관락 대신 택한 방식 — 좋아요 수 원자 UPDATE, 재고 비관락, 쿠폰 낙관락에 이은 네 번째 동시성 기법).
- **실패 격리(DLQ)**: 일시 장애는 **재시도/backoff**로 흡수하고, 정해진 횟수를 넘기거나 결정적 실패면 **DLQ로 격리**해 offset을 전진시킨다(파티션 비차단). 격리 메시지는 원문+실패 메타를 보존해 재처리 가능하게 한다(US-33). 결제(4.9)의 "확정 실패 vs in-doubt" 분류와 같은 렌즈다.

### 트래픽 제어 — 주문 대기열 (Round 8)

폭증 트래픽에서 초과 요청의 비용을 누가 치르는가의 문제다. 429 거부(Rate Limiting)는 실패 비용을 유저에게 떠넘기고 재시도 폭풍을 돌려받는다. 대기열은 그 비용을 시스템이 상태(Redis 자료구조·스케줄러·토큰 라이프사이클)로 짊어지는 대신, 유저에게 "지금 몇 번째"라는 확실성을 준다 — 유저가 기다려서라도 얻으려는 트래픽(행사)에는 후자가 맞다.

- **순서·중복 진입 보장**: 대기 순서는 Redis Sorted Set(score=진입 시각 ms, member=userId) 하나로 보관한다 — Set 특성으로 중복 진입이 자동 방지되고, 순번 조회(`ZRANK`)가 O(log N)이라 대기 인원과 무관하게 빠르다. 재진입 멱등의 핵심은 `ZADD NX`(최초 진입 시각 보존)다 — 단순 ZADD 는 재진입 시 score 를 덮어써 순번이 뒤로 리셋된다(AC-35-2). **FIFO 정밀도는 밀리초 단위**다 — 같은 ms 진입자는 member(userId) 사전순으로 tie-break 되므로 그 ms 안에서는 도착 순이 아니라 userId 순이다. 왜곡 창이 ≤1ms 라 초~분 대기에서 체감 불가능하고 특정 유저에 지속 이득도 없어(어느 ms 에 착지할지 통제 불가) 허용한 한계다. 엄격 실시간 FIFO 가 필요하면 `INCR` 단조 시퀀스를 score 로 쓰되, 재진입 멱등 보존을 위해 "존재 시 기존 score 유지"를 Lua 로 원자화해야 한다(ZADD NX 한 명령의 단순함과의 맞교환).
- **발급 속도 = min(병목들)에서 역산**: `이론 최대 TPS = min(커넥션 풀 ÷ 주문 1건 점유 시간, 핫로우 락 처리량)` 에 안전 마진 70%를 곱한다. 실측 결과 로컬 기준 구속력 있는 병목은 풀(이론 상한 ~2,500 TPS)이 아니라 **재고 핫로우 락 직렬화(~160 TPS 포화)** 였다 — 행사 상품 구성(핫로우 집중도)에 따라 상한이 수 배 움직이므로 발급 속도는 설정값으로 두고 리허설 실측 후 재산정한다.
- **발급 간격 분산(Thundering Herd 방지)**: 같은 총량이라도 1s 일괄 발급은 매초 pending 스레드 급증을 재현한다(실측: 커넥션 풀 40 포화 + 대기 150+ 스레드, 단일 핫로우 주문 p50 11배 악화). 100ms 분산 발급은 같은 총량을 10배 평탄하게 흘린다 — 처리 총량과 drain 시간은 동일하고, 간격이 사는 것은 꼬리 레이턴시와 풀의 여유다.
- **정합성(복제 지연)**: 대기열·토큰 연산은 Redis **master 로 고정**한다 — 기본 커넥션이 replica 우선이라 `ZADD` 직후 `ZRANK` 가 복제 지연으로 "대기열에 없음"을 반환할 수 있다. 연산량이 건당 O(log N) 단건이라 master 집중 부담이 없고, 읽기 분산의 이득보다 정합성이 우선.
- **스케줄러 단일 인스턴스 전제**: `ZPOPMIN` 이 원자적이라 다중 인스턴스여도 중복 발급은 없지만, 발급 속도가 인스턴스 수만큼 배가되어 산정이 무의미해진다. 스케일아웃 시 분산락(ShedLock)이 선행 조건.
- **관심사 격리**: 토큰 검증은 웹 계층(HandlerInterceptor)에 격리한다 — 주문 도메인·응용 레이어는 대기열의 존재를 모른다. 트래픽 제어는 유스케이스가 아니라 진입 지점의 관심사이므로, 대기열을 끄거나 다른 API 로 확장할 때 주문 코드는 무변경이다.
- **계층화(Rate Limiting 과 양자택일 아님)**: 봇·비정상 요청은 앞단 rate limit 으로 거부하고(대기열 자원을 정상 유저에게), 정상 유저는 대기열로 순서를 보장하며, 주문 API 자체 rate limit 이 최후 방어선으로 남는다.

### 실시간 랭킹 — 신호와 점수의 분리 (Round 9)

랭킹은 태생이 **근사 지표**다 — 몇 건의 오차가 순위를 바꿀 확률이 낮고, 데이터 수명이 하루라 어떤 오류도 하루를 넘겨 남지 않는다. 이 성질이 아래 결정들의 공통 전제다: 정확성 요구가 낮은 데이터에는 그만큼 가벼운 보장 장치를 쓰고, 아낀 비용을 교체 가능성과 관측에 투자한다.

- **Collect / Score / Serving 구간 분리(OCP)**: 수집은 사실(raw 카운트)만 쌓고, 해석(가중치)은 합성 단계의 파라미터로 둔다. 가중치를 쓰기 시점에 곱해 저장하면 이미 쌓인 점수에서 가중치를 되돌릴 수 없어 소급 변경·A/B·신호 분해가 전부 불가능해진다 — 코드 수준 분리(정책 클래스)만으로는 미래 이벤트에만 적용되는 반쪽짜리 교체 가능성만 얻는다. 대가: 서빙 신선도가 이벤트 즉시가 아니라 합성 주기 단위가 된다(유저는 분 단위 지연을 감지하지 못하므로 허용).
- **선형 가중치의 구조적 한계**: `ZUNIONSTORE WEIGHTS` 는 선형 결합만 지원한다 — log 압축 같은 **비선형 정규화는 합성 단계에서 불가능**하고, 필요해지면 수집 시점에 변환해 저장해야 한다(raw 보존 원칙과의 맞교환). 가중치 소급 교체 가능성을 얻는 대가로 받아들인 한계다.
- **명세 carry-over 예시의 결함 수정**: `ZUNIONSTORE dst 1 src WEIGHTS 0.1` 은 destination 을 덮어써 대상 보드에 이미 쌓인 점수를 지운다(잡 지연·재기동 후 재실행 등 시드보다 늦게 도는 모든 경로에서 증분 소실). 대상을 소스에 포함(`대상×1 + 원본×0.1`)하면 보존되지만 재실행 멱등이 깨지므로, SETNX 마커로 1회 실행을 보장한다 — 같은 명령이 합성에서는 멱등(자기 자신이 소스에 없음)이고 carry-over 에서는 비멱등(있음)인 이유.
- **실패 도메인 분리(projection 별 컨슈머 그룹)**: "offset 미커밋 재시도"라는 Kafka 의 기본 내구성 장치는 **실패 도메인이 분리돼 있을 때만** 작동한다 — metrics 와 dedup·그룹을 공유하면 재전달이 멱등 가드에 흡수되고, 재시도가 같은 파티션을 소비하는 metrics 처리까지 멈춘다. 그룹 분리로 랭킹의 Redis 장애 유실이 0이 되는 대신, 같은 토픽의 이중 소비 비용을 치른다. 부수 효과: 랭킹 그룹의 컨슈머 랙이 곧 랭킹 신선도 지표다.
