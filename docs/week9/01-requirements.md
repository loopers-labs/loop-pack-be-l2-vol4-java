# Requirements — 상품 랭킹 (Product Ranking)

이 문서는 상품 랭킹 기능의 요구사항과 정책을 기록한다. 공통 정책은 `docs/week2/01-requirements.md`를 따른다 — 헤더 인증(`X-USER-ID`), `ApiResponse`, 한국어 에러 메시지. 이벤트 파이프라인(주문·좋아요·조회 → Kafka → collector)은 `docs/week7`에서 만든 것을, ZSET 자료구조는 `docs/week8`에서 쓴 것을 잇는다. 이번 작업은 그 이벤트들로 실시간 랭킹판을 만들어 조회로 제공하는 일이다.

## 문제 정의 — 조회는 많고 정렬은 늘 필요하다

랭킹은 두 성질을 갖는다. 조회가 압도적으로 많고(홈 인기상품, Top-N, 인기순 정렬), 항상 정렬된 상태를 요구한다. 이걸 RDB로 풀면 매 요청이 `GROUP BY + ORDER BY`이고, 데이터가 쌓일수록 느려지며, 조회 빈도가 높아 정작 지키려던 DB를 되레 두들긴다.

또 하나 — 누적만 하면 안 된다. 역대 점수를 그대로 쓰면 옛날 상품이 상위를 독식하고(롱테일), 신상품은 노출 기회를 잃는다. 랭킹은 "언제부터 언제까지의 집계인지"가 분명해야 의미가 있다. 그래서 시간을 일 단위로 양자화해, 그날의 인기를 그날 판에서 겨루게 한다.

두 성질의 답이 Redis Sorted Set이다. 정렬을 자료구조가 내장으로 유지하고(삽입/수정 O(logN), Top-N O(N)), 날짜별 키 + TTL로 윈도우를 자연히 나눈다.

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| DB `ORDER BY` | 정합성 | 느림, 부하, 지키려던 DB를 침 |
| **Redis ZSET (택)** | 정렬 내장, 실시간 반영, 다양한 조회 | 메모리 사용, 휘발성 |

## 핵심 개념 — 랭킹은 "조회 때 계산"이 아니라 "미리 만들어둔 것을 조회"

랭킹 점수는 이벤트가 들어올 때마다 write측에서 ZSET에 누적된다. 조회는 이미 완성된 ZSET을 읽을 뿐, 그 시점에 테이블을 훑어 계산하지 않는다. 이것이 ZSET을 실시간 랭킹으로 쓰는 이유다.

### Phase 1의 저장 구조

Phase 1에서 **ranking ZSET이 유일한 랭킹 저장소**다. R7의 `product_metrics`(전체 누적)는 이번 주 **건드리지 않으며 랭킹과 무관**하다 — 전체 누적을 읽어 랭킹을 만들면 롱테일 문제로 되돌아가기 때문이다. 랭킹은 오직 이벤트에서 ZSET을 만든다.

Redis가 소실되면 그날 랭킹은 사라지고 새 이벤트로 다시 쌓인다. 랭킹은 근사 데이터라 이를 감내한다(재구축은 Phase 2).

### write / read 분리 (CQRS)

랭킹 도메인은 두 앱에 걸친 하나의 도메인이다. 컨슈머가 사는 앱과 도메인 소유는 별개다.

- **write (`commerce-streamer`)** : 이벤트를 소비해 ZSET에 점수를 쌓는다. 가중치·키 전략을 소유한다. metrics 컨슈머와 **독립된 컨슈머**(별도 group)로, 서로 읽지 않는다.
- **read (`commerce-api`)** : 완성된 ZSET을 조회해 상품정보를 붙여 응답한다.

### durability는 Phase 2

복원과 과거 조회는 Phase 2에서 다룬다. 저장소는 둘뿐이다.

| 저장소 | 역할 |
| --- | --- |
| Redis ZSET | 오늘의 실시간 랭킹 (Phase 1) |
| DB `ranking_snapshot` | 확정된 과거 랭킹(rank+score), 불변 (Phase 2) |

`metrics`는 Phase 1·2 통틀어 건드리지 않고, 별도 카운트 저장소도 두지 않는다. 과거는 자정 이후 grace를 두고 그날 ZSET을 스냅샷해 확정하며(불변), 이것이 과거 조회·재구축의 durable 원천이 된다. 상세는 아래 「콜드 스타트 & 재구축」에서 다룬다.

| 기능 | 인증 | 엔드포인트 | 설명 |
| --- | --- | --- | --- |
| 랭킹 페이지 조회 | 불필요(공개 지면) | `GET /api/v1/rankings?date=yyyyMMdd&size=20&page=1` | 해당 날짜 Top-N을 페이지로. 상품 ID가 아니라 상품 요약정보를 붙여 응답한다. `date` 생략 시 오늘. |
| 상품 상세의 순위 | 기존 상품 API 정책 | `GET /api/v1/products/{id}` | 상세 응답에 그 상품의 **오늘** 순위를 더한다. 랭킹에 없으면 `null`. |

## 점수 정책 — 가중치 합산

이벤트마다 가중치를 곱한 점수를 그 상품 member에 누적한다.

```
Score(p) += W(signal) × delta
```

| 시그널 | 이벤트 | Weight | delta | 비고 |
| --- | --- | --- | --- | --- |
| 조회 | catalog `VIEW` | 0.1 | 1 | 가장 흔해 낮게 |
| 좋아요 | catalog `LIKE` | 0.2 | ±1 | 취소는 음수 delta |
| 주문 | order `PAID` | 0.6 | quantity | 가격 무시, 수량만 |

- 주문은 매출이 아니라 **인기**를 재므로 `price`를 빼고 수량만 쓴다("많이 팔린 = 인기"). 매출 랭킹은 별도 축이다.
- `W(order)`를 가장 높게 둔다 — 실제 구매가 가장 강한 인기 신호이기 때문이다. 이 값이면 주문 1건(0.6)이 좋아요 2건(0.4)보다 위, 좋아요 3건(0.6)과는 동점이다.
- 좋아요 취소는 음수 delta로 반영해 점수가 되돌아간다: `Score += 0.2 × (-1) = -0.2`.
- 가중치는 선형이라 조회 수가 매우 크면 점수를 지배할 수 있다. 관측 후 필요하면 `log` 정규화·상한으로 완화한다(확장).

## 키 전략 & TTL

| 항목 | 값 |
| --- | --- |
| KEY | `ranking:all:{yyyyMMdd}` (일별 분리) |
| MEMBER | `productId` (예: `101`) |
| SCORE | 가중치 합산 점수 |
| TTL | 2일 (윈도우의 1.5~2배) |

- 대상 키의 날짜는 **이벤트 발행시각(`occurredAt`)을 `Asia/Seoul` 기준**으로 계산한다. **처리시각(consume 시각)이 아니다** — lag·replay로 늦게 도착한 이벤트가 엉뚱한 날 판에 들어가지 않게 한다. 이를 위해 이벤트 payload에 `occurredAt`을 싣는다.
- member는 `productId` 숫자만 쓴다 — 이 판에는 상품만 들어가고 KEY가 이미 맥락(ranking)을 말하므로, prefix 없이 파싱 비용을 아낀다.
- TTL 2일이면 자정이 지나도 어제 판을 조회할 수 있고, 메모리는 자동 회수된다.

## 적재 방식 — 이벤트마다가 아니라 배치로 모아서

컨슈머는 배치 리스너다(`max.poll.records=3000`, concurrency 3, manual ack). `max.poll.records`는 **상한**이지 목표가 아니다 — 한 `poll()`은 그 시점에 쌓인 만큼(최대 3000)을 돌려주고, 이만큼 모일 때까지 기다리지 않는다. 부하가 높으면 배치가 커지고 한가하면 소량이다(배치를 더 모으려면 `fetch.min.bytes`/`fetch.max.wait.ms`로 조절 — 반영 지연과 트레이드오프). 배치에 도착한 이벤트를 `(날짜키, member)`별로 접어(fold) 점수 델타를 합친 뒤, 파이프라인으로 한 번에 flush한다.

```
한 poll = 최대 3000 이벤트 (부하에 따라 가변). 예: 3000건이 300개 상품에 분산될 때

즉시 호출 : ZINCRBY 3000회 = 왕복 3000번 → RTT가 병목 → 컨슈머 lag 누적
fold+pipe : (날짜키,member)별 합산 → ZINCRBY 300회 → 파이프라인 1왕복
```

- fold+pipeline의 이득은 **배치 크기에 비례**한다. 바쁠 때(큰 배치) 크게 아끼고, 한가할 때(작은 배치)는 어차피 할 일이 적다 — 부하가 몰릴 때 정확히 값이 나오는 구조다.
- 즉시 호출은 왕복이 병목(RTT-bound)이 된다. 한 배치에 서로 다른 날짜(`occurredAt`)가 섞일 수 있으므로 fold 키는 `(날짜키, member)`다.
- 점수 누적은 `ZINCRBY`다. 멱등이 아니라 재소비 시 중복 가산된다. 재전달은 드물고 판은 하루면 리셋되며 랭킹은 근사 데이터라, 이 drift를 **허용**한다. 이벤트 ID 기반 멱등은 넣지 않는다.

## 조회 정책

- **서빙 창 = 최근 2일(오늘·어제)**. ZSET TTL과 같은 창이다.
- 랭킹 페이지는 `ZREVRANGE`로 Top-N의 `(member, score)`를 뽑고, 그 ID들을 product 도메인에서 `findAllById`로 **한 번에** 조회해 요약정보(상품명·가격 등 목록 카드 수준)를 붙인다. 상세 전체를 담지 않고, ID를 하나씩 조회(N+1)하지 않는다.
- 페이지네이션은 `ZREVRANGE`의 `start/end`(`= (page-1)×size, page×size-1`)로 처리하고, 전체 수는 `ZCARD`로 준다.
- 상품 상세의 순위는 오늘 키에 `ZREVRANK`로 조회한다. 0-based이므로 +1해 표기하고, 없으면 `null`.
- 조회 결과 구분:

| 요청 | 응답 |
| --- | --- |
| 창 안 + 데이터 있음 | 200, 랭킹 목록 |
| 창 안 + 아직 없음(콜드스타트) | 200, 빈 목록 |
| 창 밖(더 과거 / 미래) | 404 `RANKING_NOT_AVAILABLE` (Phase 1). Phase 2: 확정된 과거일은 스냅샷 서빙, 미래·미확정은 404 |
| 형식 오류(`date=abc`) | 400 `RANKING_INVALID_DATE` |
| Redis 장애(폴백) | 200, `like_count` 내림차순 목록 + `degraded:true` |

- **Redis 장애 폴백(Phase 1).** ZSET 조회가 실패하면 DB `like_count` 내림차순 상품 목록으로 폴백하고 `degraded:true`를 내린다. 좋아요 수는 DB 컬럼(like 도메인이 이벤트로 갱신 + Reconciler 보정)이라 **Redis 없이 동작**한다. `like_count`는 전체 누적(롱테일)이라 정상 랭킹(일간)과 다르며, 그 차이를 flag가 알린다 — 클라이언트는 이 목록을 인기 배지 없이(예: "신규/추천") 표시한다. 상세(단건 순위)는 `todayRank`만 `null`로 떨궈 상세 자체는 막지 않는다.

## 콜드 스타트 & 재구축 (Phase 2)

Phase 2는 "과거 = 불변, 현재 = 실시간" 프레임을 둔다. 저장소는 Redis ZSET(현재)와 DB `ranking_snapshot`(확정된 과거) 둘뿐이며, `metrics`는 건드리지 않는다.

### 콜드 스타트 — Score Carry-Over (23:50)

윈도우가 바뀌는 자정 직후에는 점수가 쌓이지 않아 랭킹이 비거나 빈약하다. 완화책은 전날 판의 점수 일부를 작은 가중치로 미리 심는 것이다: 다음 날 ZSET = `0.1 × 오늘 ZSET 점수`. 작은 가중치라 오늘의 실제 활동이 금방 위로 올라온다.

- **23:50에 스케줄러**가 다음 날 키를 오늘 ZSET에서 미리 seed한다(단일 실행 **락 + 재시도 + 실패 알림**).
- 조회(read)가 유발하지 않는다 — read는 순수 조회로 두고, 빈 창은 200 빈 목록으로 답한다. 자정 직전 빈 창은 항상 오류가 아니다(시스템 첫날, 어제 활동 없는 상품). read-repair를 넣지 않는 이유다.

### finalize — 과거 확정 스냅샷 (00:30)

`occurredAt`으로 버킷팅하므로 자정을 넘겨 늦게 도착한 어제 이벤트가 어제 ZSET에 계속 반영된다. 그래서 어제를 **00:00 정각이 아니라 grace를 둔 00:30에** 확정한다.

- **00:30에 스케줄러**(락)가 어제 ZSET을 `ZREVRANGE`로 떠서 DB `ranking_snapshot`(날짜, 상품, rank, score)에 저장한다. 저장된 과거는 **불변**이다.
- 확정된 과거는 **DB 스냅샷에서 조회**한다 — Redis TTL(2일) 창을 넘어서도 서빙되며, Phase 1의 404가 이 범위에서 완화된다.
- grace 30분은 컨슈머 lag 실측으로 정한다. lag이 그 이상이면 꼬리 이벤트 몇 개가 스냅샷에서 빠질 수 있으나 드물고 손실이 작다.

### 재구축 — Redis 소실 복구

Redis가 소실되면 그날 ZSET을 다시 만든다. 소스는 **어제 스냅샷**이다(`metrics` 아님).

```
rebuilt(오늘) = 0.1 × 어제 스냅샷 점수  +  오늘 이벤트 재축적
```

- **트리거는 수동/운영**이다. 모니터링 알림 → 운영자가 재구축 엔드포인트를 호출한다. Redis 소실은 드문 사건이라 자동 감지 인프라는 두지 않는다(확장).
- 재구축은 **임시 키에 쓰고 `RENAME`으로 원자 교체**한다 — 살아난 컨슈머의 실시간 `ZINCRBY`와 레이스를 막는다.
- **알려진 한계**: 스냅샷은 확정된 날만 보호한다. 크래시가 finalize(00:30) 전에 나면 그 날은 유실된다(과거라 영향 적고 랭킹은 근사라 감수). 스냅샷은 최종 점수만 저장하므로 가중치를 바꿔도 과거는 재계산하지 않는다(과거는 불변).

### 정밀 finalize — 워터마크 (확장)

grace 30분은 "lag < 30분" 가정의 근사다. 정밀하게 하려면 파티션별 최대 `occurredAt`을 추적해 글로벌 워터마크가 자정을 넘긴 시점에 확정하거나(idle 파티션 보정 필요), 경계 마커 이벤트를 흘려 확정을 신호할 수 있다. 대규모에선 Kafka Streams/Flink의 event-time window + allowed-lateness가 이를 기본 제공한다. 이번 범위는 고정 grace로 둔다.

## 단계 구분

| Phase | 범위 | 포함 |
| --- | --- | --- |
| **Phase 1 (Must)** | 실시간 파이프라인 + 조회 + 읽기 폴백 | 컨슈머 fold → `ZINCRBY`, 랭킹 페이지 API, 상품 상세 순위, Redis 장애 읽기 폴백(목록=좋아요순+`degraded` / 상세=순위 `null`). `metrics` 미변경 |
| **Phase 2 (Nice)** | 신선도·복원력 | carry-over(23:50), finalize 스냅샷(00:30)·과거 조회, 재구축(수동 트리거), 시간별 랭킹 |

## 장애 시나리오 & 리스크

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| Redis 소실 | 그날 랭킹 사라짐 | **읽기 폴백(Phase 1)**: 목록=`like_count`순+`degraded`, 상세=순위 `null`. **쓰기**: 새 이벤트로 재축적. Phase 2: 어제 스냅샷에서 수동 재구축(temp/RENAME) |
| 재소비 중복 | `ZINCRBY` 중복 가산으로 점수 부풀림 | 드물고 하루면 리셋 → 허용(drift). 멱등 미도입 |
| 처리시각 버킷팅 | 늦은 이벤트가 잘못된 날 판에 반영 | 이벤트 `occurredAt`(KST)로 키 계산 |
| 조회 폭주 | 인기 지면이라 조회가 집중됨 | ZSET 조회가 μs 단위. 필요 시 Top-N 결과 캐싱(확장) |
| 조회수 지배 | 조회 많은 상품이 상위 독식 | 선형 유지, 관측 후 `log`/상한(확장) |
| 콜드스타트 | 자정 직후 빈 랭킹 | carry-over 스케줄러 (Phase 2) |

## 에러 코드 (`RankingErrorCode`)

| 코드 | ErrorType | 상황 |
| --- | --- | --- |
| `RANKING_INVALID_DATE` | BAD_REQUEST | `date` 파라미터 형식 오류 |
| `RANKING_NOT_AVAILABLE` | NOT_FOUND | 서빙 창(최근 2일) 밖 날짜 조회 |

## 범위에서 제외

- **멱등 적재.** 이벤트 ID 기반 중복 제거는 넣지 않는다(drift 허용).
- **자동 재구축 감지.** Redis 소실을 자동 감지해 재구축하는 것은 확장. Phase 2는 수동 트리거까지.
- **시간별(1시간) 랭킹.** 일간을 base로 두고 Phase 2에서 확장한다.
- **실시간 가중치 조절.** 가중치를 런타임에 바꾸는 것은 확장이다.
- **조회수 log 정규화.** 선형으로 시작하고, 조회 지배가 관측되면 도입한다.
- **개인화·큐레이션 폴백.** 콜드스타트를 에디토리얼 픽으로 채우는 것은 범위 밖이다.
- **`metrics` 전체 누적의 활용.** 전체 누적을 읽는 기능(역대 통계 등)은 이번 범위 밖이며, 랭킹은 이를 읽지 않는다.
