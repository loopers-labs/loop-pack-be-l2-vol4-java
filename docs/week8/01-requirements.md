# Requirements — 주문 대기열 (Order Queue)

이 문서는 주문 API 앞단에 두는 대기열 기능의 요구사항과 정책을 기록한다. 공통 정책은 `docs/week2/01-requirements.md`를 따른다 — 헤더 인증(`X-USER-ID`), `ApiResponse`, 한국어 에러 메시지. 주문 이후 흐름(이벤트 발행 → Kafka → collector 집계)은 `docs/week7`에서 만든 파이프라인을 그대로 잇는다. 이번 작업은 주문을 바꾸지 않고, 주문 앞에 관문을 하나 세우는 일이다.

## 문제 정의 — 기능이 아니라 트래픽 제어

블랙 프라이데이에 주문이 평소 초당 100건에서 초당 10,000건으로 튄다. 서버를 열 배 늘려도 DB 커넥션 풀과 PG는 그만큼 늘지 않는다. 피크가 짧고 높아서 오토스케일링이 반응하기 전에 터진다. 그래서 진짜 해결해야 할 문제는 "주문을 더 빨리 처리하는 것"이 아니라, **하류가 감당할 수 있는 속도로만 요청을 흘려보내는 것**이다. 이걸 back-pressure라고 부른다.

트래픽이 몰릴 때 선택은 둘이다. 초과분을 거부하거나(Rate Limiting), 보관하거나(Queuing). 주문은 유저가 화면 앞에서 결과를 기다리는 요청이다. "나중에 다시 시도하세요"를 돌려주면 유저는 더 세게 새로고침한다. 그래서 거부가 아니라 **줄을 세워 순서대로 들여보내는** 쪽을 택한다.

세 관점으로 다시 풀면 이렇다.

| 관점 | 재해석된 문제 |
| --- | --- |
| 사용자 | 몰려도 내 순번과 "약 N분"을 보며 기다릴 수 있어야 한다. 새로고침해도 자리를 잃지 않아야 한다. |
| 비즈니스 | 피크에도 시스템이 죽지 않고, 먼저 온 사람이 먼저 처리되는 공정한 순서를 지켜야 한다. 대기 중 이탈을 줄여야 한다. |
| 시스템 | 하류(DB 커넥션 풀)가 감당하는 속도로만 상류를 흘려보낸다. 스케줄러가 발급 속도를 제어하고, 커넥션 풀(40 · 3s 타임아웃) 자체가 동시성 상한 = 최종 방어선이 된다. |

## 핵심 개념 — 유저가 지나는 세 구간

한 유저는 대기 → 입장 → 처리(또는 만료)의 세 구간을 지난다.

- **대기(WAITING)** — 대기열에 순번으로 존재한다. Redis Sorted Set에 진입 시각을 점수로 넣어, 먼저 온 사람이 앞 순번을 갖는다.
- **입장(ADMITTED)** — 스케줄러가 앞에서 꺼내 입장 토큰을 발급한 상태다. 토큰이 있는 유저만 주문 API로 들어갈 수 있다. 토큰은 5분 뒤 자동 만료된다.
- **처리/만료(ORDERED/EXPIRED)** — 토큰으로 주문을 마치면 토큰을 지운다. 5분 안에 쓰지 않으면 토큰이 만료돼 자리를 반납한다.

## 제공 기능

| 기능 | 인증 | 엔드포인트 | 설명 |
| --- | --- | --- | --- |
| 대기열 진입 | USER 필요 | `POST /api/v1/queue/enter` | 대기열에 유저를 넣고 순번을 응답한다. 이미 있으면 순번을 유지한다. |
| 순번 조회 | USER 필요 | `GET /api/v1/queue/position` | 현재 순번·예상 대기시간·다음 폴링 간격을 응답한다. 토큰이 발급됐으면 토큰을 함께 준다. |
| 주문 | USER + 입장 토큰 | `POST /api/v1/orders` | 기존 주문 API에 토큰 검증 관문을 더한다. 토큰이 유효할 때만 처리한다. |

## 정책 규칙

### 진입과 중복

- 진입은 로그인 유저만 가능하다. 대기열의 member로 `userId`를 쓴다. 같은 유저가 탭을 여러 개 열어도 순번은 하나로 합쳐진다 — 중복 진입이 자료구조 특성으로 자동 방지된다.
- 재진입(새로고침 포함)은 순번을 유지한다. `ZADD NX`로 넣어, 이미 줄에 있으면 아무 일도 하지 않고 현재 순번을 돌려준다. 새로고침이 자리를 뒤로 미는 일은 없다.
- 대기열에 없는 유저가 순번을 조회하면 "대기열에 없음"을 명시적으로 안내한다. 조회가 진입을 유발하지 않는다. 진입은 오직 `enter`로만 일어난다.

### 발급 (스케줄러)

- 스케줄러가 일정 주기(기본 200ms)마다 대기열 앞에서 정해진 인원(batch)을 꺼내 입장 토큰을 발급한다. 꺼내기는 원자적 연산으로, 같은 유저가 두 번 꺼내지지 않는다.
- 꺼내는 인원은 "지금 몇 명이 입장해 있는지"를 세지 않고 **매 주기 고정 인원**으로 흘려보낸다. 만료로 자리가 나면 발급이 계속 돌기 때문에 추가 보정 없이도 자연히 채워진다.
- 인스턴스가 여러 대여도 스케줄러는 한 대만 발급해야 한다. Redis 락으로 매 주기 한 대만 통과시킨다. 락은 발급 속도가 인스턴스 수만큼 뻥튀기되는 것을 막기 위한 것이다.

### 토큰

- 토큰은 유저별로 Redis에 저장하고 TTL(기본 5분)을 건다. 주문 API 진입 시 검증하고, 주문을 마치면 삭제한다. 한 번 쓰면 끝나는 단발성이다.
- 미사용 토큰은 TTL로 자동 만료된다. 만료된 몫은 스케줄러가 계속 발급하며 다음 유저에게 돌아간다.

### 주문 게이트

- 대기열은 항상 켜져 있고, 주문은 유효한 토큰이 있어야만 처리된다. 이벤트에만 켜는 토글은 이번 범위에 넣지 않는다(확장으로 언급만).
- 토큰이 유효해도 주문의 동시 처리 수에는 상한이 필요하다 — 스케줄러가 평균 발급 속도를 눌러도 한 주기 안에서 순간적으로 몰리는 스파이크가 있기 때문이다. 이 상한은 **별도 장치 없이 HikariCP 커넥션 풀이 이미 제공한다**: 동시 40개까지 처리하고, 초과분은 3초(connection-timeout) 대기하다 자리가 나면 진행한다. 즉 풀이 곧 Bulkhead다. 근거는 [처리량 산정](#처리량-산정) 참고.

### 예상 대기시간

- `순번 / 목표TPS`로 계산해 "약 N분/초"로 보여준다. 정확한 값이 아니라 추정치이므로 반올림해 표현한다.
- 목표TPS는 발급 배치 크기를 정하는 값과 같다(하나의 설정을 공유한다). 안내 문구와 실제 발급 속도가 어긋나지 않게 하려는 것이다.

## 처리량 산정

주문 하나가 커넥션을 얼마나, 얼마 동안 점유하는지로 안전 처리량을 정한다.

```
DB 커넥션 풀 40 · 주문 1건 평균 200ms(가정)
→ 이론상 최대 = 40 / 0.2 = 200 TPS
→ 안전 마진 70% = 140 TPS
→ batch-size = 140 × (200ms / 1000) = 28명 / 주기
```

이 숫자는 발제·가정에 기댄 추정치다. 완성 전후로 k6 부하 테스트를 돌려 실제 한계(무릎)를 재고, 그 값으로 `batch-size`를 조정한다. 자세한 측정 계획은 `06-k6-load-test.md`에 둔다.

**커넥션 풀이 곧 Bulkhead다.** 별도 resilience4j Bulkhead를 두지 않는다. HikariCP가 이미 동시성 세마포어이기 때문이다.

| 풀 설정 | 값 | Bulkhead 대응 |
| --- | --- | --- |
| `maximum-pool-size` | 40 | 동시 처리 상한 (maxConcurrentCalls) |
| `connection-timeout` | 3000ms | 초과분 대기 시간 (maxWaitDuration) — 즉시 거절이 아니라 3초 흡수 |

스케줄러 발급률이 유입을 풀 처리량 이하로 누르므로 대기(3초)가 발동할 일 자체가 드물다. 거절은 3초로도 안 될 만큼 지속 과부하일 때만 일어나며, 그때는 한 명 재시도가 풀 붕괴보다 낫다. connection-timeout이 3초로 짧아 대기 요청이 톰캣 스레드를 오래 붙잡지도 않는다.

```
order-queue.admission.interval-ms  : 200
order-queue.admission.batch-size   : 28   # = 목표TPS × interval/1000 (k6 실측 후 조정)
order-queue.entry-token.ttl-seconds: 300
```

## 장애 시나리오 & 리스크

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 스케줄러 정지 | 대기열에서 아무도 빠지지 못함 | 락 TTL을 주기와 같게 둬, 홀더가 죽으면 다음 주기에 다른 인스턴스가 이어받음. 정지 알림은 확장. |
| Redis 장애 | 대기열·토큰 전부 소실 | 장애 시 동작(차단/우회/폴백)을 사전 정의해야 함. 이번 범위에서는 정책만 열어두고 구현은 보류. |
| 토큰 미사용(만료) | 발급했는데 자리만 차지 | TTL 자동 만료 + 발급이 계속 돌아 흡수. 전환율/만료율 지표는 확장(active 구조 추가 시). |
| Thundering herd | 발급 직후 동시 주문으로 순간 스파이크 | 발급을 잘게 분산(200ms마다 소수) + 커넥션 풀(40 · 3s)이 순간 스파이크를 흡수. |
| 과도한 폴링 | 대기 인원 × 폴링 = 조회 부하 | 순번 구간별로 폴링 간격을 늘려 응답에 실어 보냄(`pollAfterMs`). |

## 범위에서 제외

- **Redis 장애 폴백.** 전면 차단/우회/폴백 큐 중 무엇을 할지는 별도 결정으로 남긴다. 정답이 없으므로 "장애 시 어떻게 동작할지"를 정의해두는 것 자체가 다음 과제다.
- **SSE(실시간 push).** 순번 알림을 폴링 대신 SSE로 밀 수도 있지만, 대기 인원만큼 연결을 상시 유지해야 해 crowd 규모가 곧 연결 수 병목이 된다. 폴링(+동적 간격)은 연결을 붙잡지 않아 이 워크로드에 더 맞는다 — 폴링으로 확정.
- **명시적 Bulkhead(resilience4j).** 커넥션 풀(40 · 3s)이 이미 Bulkhead 역할을 해 중복이다. fail-fast·관측 지표가 필요해지면 그때 추가한다.
- **토큰 Jitter.** 발급을 잘게 나누는 것으로 떼몰이를 이미 대부분 완화한다. 활성 시점 랜덤 딜레이는 넣지 않는다.
- **입장 인원 지표(active 구조).** 발급 로직에는 필요 없다. 전환율·만료율을 재려면 그때 별도 구조를 더한다.
- **큐 on/off 토글.** 이번엔 항상 켜둔다. 이벤트별 토글은 확장이다.
- **어뷰징(멀티 계정) 대응.** member=userId로 한 유저의 중복은 막지만, 계정을 여러 개 만드는 것은 이번 범위 밖이다.
