# 01. 요구사항 명세 — Redis 기반 대기열 시스템 (Virtual Waiting Room)

> **⚠️ 설계 변경 (2026-07-08): admission 모델을 정원제 → 방류형(rate-based)으로 전환**
> 본 문서의 NFR-3/4·P-5·§9-D2·D6는 **정원제**(활성 인원을 `maxActive` 상한으로 유지, 매 주기 빈자리만 리필) 기준으로 작성됐다. 이후 **방류형**으로 전환: 매 **M초**마다 대기열 앞에서 **N명 고정 방류**(활성 점유량 무관, throughput=N/M). 노브는 `release-size(N)`·`scheduler-interval-seconds(M)`. 활성 상한(back-pressure by occupancy)이 없어지는 대신 방류 레이트가 admission을 제어하고, 다중 인스턴스 방류 총합은 Lua 윈도우 레이트리밋으로 N/주기에 고정한다. 관련 절에 `[방류형]` 갱신을 표기했다. 방류형의 안전 조건(동시 부하 ≈ N/M × TTL)과 TTL 재해석은 [`06-loadtest-ttl.md`](./06-loadtest-ttl.md) 참조.

## 0. 이 문서의 역할

- 도메인 객체·컴포넌트 모델 → [`03-class-diagram.md`](./03-class-diagram.md)

> **기존 자산과의 관계**: 대기열은 **주문 API 앞단의 관문**일 뿐이다. 유저가 관문을 통과해 주문 API에 진입한 뒤의 흐름(주문 생성 → 결제 → 이벤트 발행 → Kafka 파이프라인 → `product_metrics` 집계)은 week6~week7에서 구축한 구조를 **그대로 재사용**한다. 이번 주차는 그 앞에 "누가 언제 들어올 수 있는가"를 제어하는 계층만 추가한다.

## 1. 개요

지금까지 주문 API는 요청이 오는 즉시 재고 확인·쿠폰 적용·결제 시작을 수행했다. 평시에는 문제가 없지만, 블랙 프라이데이처럼 특정 시각에 수만 명이 동시에 몰리면 DB 커넥션 풀이 즉시 고갈되고, 대기 요청이 쌓이며 응답 지연·타임아웃·연쇄 장애로 번진다. 큐잉 없이 "먼저 온 요청이 먼저 처리된다"는 보장도 없다.

week8의 목표는 세 단계다.

1. **대기열 진입 (Step 1)** — 유저는 주문 API를 직접 호출하는 대신 먼저 **대기열에 진입**한다. Redis Sorted Set으로 진입 순서(FIFO)를 보장하고, 같은 유저의 중복 진입을 방지한다. 진입 후 자신의 순번(rank)과 예상 대기 시간을 조회할 수 있다.
2. **입장 토큰 & 스케줄러 (Step 2)** — 스케줄러가 일정 주기로 대기열 앞에서 **N명씩** 꺼내 **입장 토큰**을 발급한다. 토큰은 TTL을 가져 일정 시간 내 사용하지 않으면 자동 만료된다. 토큰을 가진 유저만 주문 API에 진입할 수 있고, 주문 완료 시 토큰은 삭제된다. 배치 크기 N은 **시스템 처리량(DB 커넥션 풀 × 평균 처리 시간)** 을 근거로 산정한다.
3. **실시간 순번 조회 (Step 3)** — 대기 중인 유저가 현재 순번과 예상 대기 시간을 **실시간(Polling)** 으로 확인할 수 있는 API를 제공한다. 대기 인원 규모에 따른 Polling 부하를 고려해 갱신 주기·캐싱 전략을 정한다.

> **운영 관점**: 대기열의 존재 이유는 "공정성"과 "백프레셔(back-pressure)"다. 처리 가능한 만큼만 입장시켜 백엔드를 일정 부하로 유지(admission control)하고, 나머지는 대기시켜 초과 트래픽을 흡수한다. 따라서 배치 크기·주기는 감(感)이 아니라 처리량 설계 기준에서 도출되어야 한다.

## 2. 범위 (Scope)

### In scope

- **Step 1 — Redis 기반 대기열**
  - Redis Sorted Set(ZSET)으로 대기열 진입, 진입 순서(score) 기반 FIFO 보장.
  - 같은 유저의 중복 진입 방지(멱등 진입).
  - 유저 본인의 순번(rank)·예상 대기 시간 조회.
- **Step 2 — 입장 토큰 & 스케줄러**
  - 스케줄러가 주기적으로 대기열 앞에서 N명 pop → 입장 토큰 발급.
  - 토큰 TTL(미사용 시 자동 만료).
  - 주문 API 진입 가드: 유효한 토큰 보유자만 통과.
  - 주문 완료 시 토큰 삭제(1회용).
  - 배치 크기 N 산정 근거 문서화(DB 커넥션 풀 · 평균 처리 시간 기반).
- **Step 3 — 실시간 순번 조회**
  - 순번·예상 대기 시간 조회 API(Polling 기반).
  - 대기 인원에 따른 Polling 부하 완화(권장 폴링 주기, 조회 결과 캐싱 등).
- 대기열이 보호하는 대상은 **주문 API**로 한정한다.

### Out of scope

- 주문 API **이후** 흐름 변경 — 주문 생성/재고 차감/결제/이벤트 발행/Kafka/Metrics는 week6~week7 구조를 그대로 사용하며 이번 주차에서 로직을 바꾸지 않는다.
- WebSocket/SSE 기반 실시간 푸시 — 이번엔 **Polling** 으로 한정(푸시는 Open Question).
- 대기열 자체의 다중 상품·다중 이벤트 분리(상품별 큐, 이벤트별 큐) — 단일 글로벌 큐로 시작하되 키 네이밍은 확장 가능하게 설계.
- 봇/어뷰징 방지(캡차, IP 레이트리밋) — 대기열 진입 인증은 기존 유저 식별 체계에 의존.
- 대기열 진입 이전의 정적 대기 페이지(프론트) 구현 — 백엔드 API까지만.

## 3. 용어 정의 (Glossary)

| 용어 | 정의 |
|------|------|
| 대기열 (Waiting Queue) | 주문 API 진입을 기다리는 유저들의 순서 집합. Redis Sorted Set으로 구현. |
| 진입 (Enqueue) | 유저가 대기열에 자신을 등록하는 행위. 순서(score)가 부여된다. |
| 순번 (Rank) | 대기열에서 자신의 앞에 있는 인원 수 기반 위치(0-based 또는 1-based). |
| 입장 토큰 (Entry Token / Pass) | 스케줄러가 대기열 앞부분 유저에게 발급하는, 주문 API 진입 자격 증명. TTL 보유. |
| 활성 세트 (Active Set) | 현재 입장 토큰을 발급받아 주문 API를 이용할 수 있는 유저 집합. |
| 배치 크기 (N) | 스케줄러가 한 주기에 대기열에서 꺼내 입장시키는 인원 수. |
| 처리량 (Throughput) | 시스템이 단위 시간당 완료할 수 있는 주문 수. `DB 커넥션 풀 크기 / 평균 처리 시간`으로 근사. |
| 예상 대기 시간 (ETA) | `내 순번 / 처리량` 으로 추정한, 입장까지 남은 시간. |
| Polling | 클라이언트가 일정 주기로 순번 조회 API를 반복 호출해 상태를 갱신하는 방식. |

## 4. 액터 & 인증 (Actors & Auth)

- **User** — 대기열에 진입하고 순번을 조회하며, 입장 토큰을 받아 주문 API를 호출하는 일반 사용자. 기존 주차와 동일한 유저 식별 체계(요청 헤더 기반 사용자 식별, 예: `X-USER-ID`)를 사용한다.
- **Scheduler (System Actor)** — 애플리케이션 내부의 주기 실행 컴포넌트. 사람 요청이 아니라 서버가 자체 실행한다. 대기열에서 N명을 꺼내 토큰을 발급한다. (인증 대상 아님. 단일 인스턴스 실행 보장은 아래 NFR 참조.)
- **Admin (선택)** — 대기열 현황(총 대기 인원, 활성 인원, 배치 크기) 조회·조정. 최소한 운영 지표 조회는 제공하되, 실제 노출 범위는 Open Question.

> 인증 관련 주의: **입장 토큰**은 유저 식별과 별개의 "진입 자격" 증명이다. 주문 API는 (1) 기존 유저 인증 + (2) 유효한 입장 토큰 두 가지를 모두 요구한다. 토큰은 발급받은 본인만 사용할 수 있어야 한다(토큰 ↔ 유저 바인딩).

## 5. 도메인 모델 개요

이 주차는 신규 **비즈니스 도메인**을 추가하지 않는다. 대신 대기열을 구성하는 **인프라/애플리케이션 컴포넌트**와 **Redis 자료구조**를 정의한다. (실제 키 설계는 `04-redis-model.md`.)

- **WaitingQueue** — 대기 중 유저들의 순서 집합.
  - 저장소: Redis Sorted Set. member=userId, score=진입 시각(또는 단조 증가 시퀀스).
  - 책임: 진입(중복 방지), 순번 조회, 앞에서 N명 pop.
- **EntryToken (Pass)** — 주문 API 진입 자격.
  - 저장소: Redis String/Hash + TTL (예: `pass:{token}` → userId, 또는 활성 세트 `active:users` ZSET with TTL 개념).
  - 속성(예상): token(불투명 문자열), userId, issuedAt, expiresAt(TTL), status(발급/사용/만료).
  - 책임: 발급, 유효성 검증(존재 + 미만료 + 유저 일치), 사용 후 삭제.
- **QueueScheduler** — 주기 실행 컴포넌트.
  - 책임: 매 주기 활성 여유분만큼 대기열에서 pop → 토큰 발급. 단일 실행 보장 필요.
- **QueuePolicy / ThroughputConfig** — 처리량·배치 크기 산정 설정.
  - 속성(예상): dbPoolSize, avgProcessSeconds, schedulerIntervalSeconds → 파생값 batchSize, maxActive.
- **관계**: WaitingQueue —(pop N)→ Scheduler —(발급)→ EntryToken —(검증/소모)→ 주문 API. 주문 완료 시 EntryToken 삭제 → 활성 여유분 증가 → 다음 주기에 다음 N명 입장.

## 6. 기능 요구사항 (Functional Requirements)

> API 경로·헤더·상태코드는 제안값이며, 확정 전 Open Questions에서 조정한다. 기존 주차 컨벤션(`/api/v1/...`, `X-USER-ID` 헤더)을 따른다.

### 6.1 대기열 (Step 1)

#### FR-1. 대기열 진입
- **What**: 유저가 대기열에 진입하고, 부여된 순번 정보를 받는다.
- **API**: `POST /api/v1/waiting-queue/enter` — 유저 인증 필요(`X-USER-ID`).
- **Response(예상)**: `{ userId, rank, aheadCount, estimatedWaitSeconds, alreadyIn }`
- **Rules**:
  - Redis ZSET에 `ZADD ... NX`(또는 존재 검사)로 등록. **이미 진입한 유저는 재진입해도 순번이 유지된다**(멱등, 순번 밀림 금지).
  - score는 진입 시각(ms) 또는 단조 증가 시퀀스로 부여해 FIFO를 보장한다. 동시 진입 시 score 충돌로 순서가 뒤바뀌지 않도록 처리(시퀀스/타이브레이커).
  - 이미 **입장 토큰을 보유(활성 상태)** 한 유저가 진입 요청 시: 재진입시키지 않고 "이미 입장 가능" 상태를 반환.
- **Errors**: 유저 식별 누락 → 401/400. Redis 장애 → 503(대기열 사용 불가).

#### FR-2. 내 순번 조회 (기본)
- **What**: 유저가 자신의 현재 순번과 예상 대기 시간을 조회한다.
- **API**: `GET /api/v1/waiting-queue/rank` — 유저 인증 필요.
- **Response(예상)**: `{ userId, status, rank, aheadCount, estimatedWaitSeconds }` — status ∈ {WAITING, READY(토큰 발급됨), NOT_IN_QUEUE, EXPIRED}
- **Rules**:
  - 순번 = `ZRANK(queue, userId)` 기반. 대기열에 없으면 NOT_IN_QUEUE.
  - 예상 대기 시간 = `aheadCount / throughput`. throughput은 QueuePolicy에서 파생.
  - 토큰이 이미 발급된 유저는 status=READY로 응답(주문 API로 진행하라는 신호).
- **Errors**: 유저 식별 누락 → 401/400.

### 6.2 입장 토큰 & 스케줄러 (Step 2)

#### FR-3. 입장 토큰 발급 (스케줄러)
- **What**: 스케줄러가 주기적으로 대기열 앞에서 N명을 꺼내 입장 토큰을 발급한다.
- **트리거**: 서버 내부 스케줄러(고정 주기, 예: 1~5초). 외부 API 아님.
- **Rules**:
  - ~~매 주기 발급 인원 = `min(N, maxActive − 현재 활성)`(정원제 리필)~~ → **[방류형]** 매 주기 방류 인원 = 이번 M초 윈도우 여유분 `N − 윈도우_방류누계`(다중 인스턴스 합산 ≤ N). 활성 점유량과 무관.
  - `ZPOPMIN(queue, k)`로 앞에서 k명 pop → 각 유저에 대해 토큰 생성(불투명 문자열) → `pass:{token}=userId` 저장 + **TTL 설정** → 활성 세트에 등록. (§04 §3.1 Lua로 원자 실행)
  - 발급된 유저의 대기열 status는 READY로 전환(대기열에서 제거됨).
  - 스케줄러는 다중 인스턴스 환경에서도 **한 번만** 실행되어야 한다(분산 락/리더 선출 — 기존 ShedLock 자산 재사용 가능).
- **Errors**: Redis 장애 시 발급 스킵(다음 주기 재시도), 로그·메트릭 기록.

#### FR-4. 토큰 TTL 만료
- **What**: 발급된 토큰이 일정 시간 내 사용되지 않으면 자동 만료된다.
- **Rules**:
  - 토큰 TTL **30초**(§9-D1 개정, [`06`](./06-loadtest-ttl.md))로 Redis가 자동 삭제.
  - 만료된 토큰으로 주문 API 진입 시 거부(만료 응답). 유저는 필요 시 재진입(대기열 뒤로).
  - 만료로 비워진 활성 여유분은 다음 스케줄러 주기에 다음 대기자에게 배정된다.

#### FR-5. 주문 API 진입 가드
- **What**: 토큰 보유자만 주문 API에 진입할 수 있다.
- **API**: 기존 주문 생성 API `POST /api/v1/orders`에 **입장 토큰 요구** 추가. 헤더 `X-QUEUE-TOKEN`(§9-D4).
- **Rules**:
  - 가드는 (a) 토큰 존재 + (b) 미만료 + (c) 토큰↔유저 일치를 검증한다. 하나라도 실패 시 진입 거부.
  - 검증 통과 시에만 기존 주문 로직(week6~7) 실행.
  - **주문 완료(성공 확정) 시 토큰 삭제** → 1회용. 삭제로 활성 여유분 회복.
  - **주문 실패 시 토큰은 즉시 회수하지 않고 TTL까지 재시도를 허용한다(§9-D3)**. 일시적 실패(재고 순간부족·PG 타임아웃)로 유저를 대기열 뒤로 보내지 않는다. 미사용 시 TTL이 회수한다.
- **Errors**: 토큰 없음/만료/불일치 → 403(대기열 재진입 유도).

### 6.3 실시간 순번 조회 (Step 3)

#### FR-6. 실시간 순번/ETA 조회 (Polling)
- **What**: 대기 중 유저가 순번·예상 대기 시간을 실시간에 가깝게(Polling) 조회한다.
- **API**: FR-2와 동일 엔드포인트를 Polling 대상으로 사용(`GET /api/v1/waiting-queue/rank`).
- **Rules**:
  - 응답에 **권장 폴링 주기**(예: `pollAfterSeconds`)를 포함해 클라이언트 폴링 간격을 서버가 제어(대기 인원 많을수록 간격 확대).
  - 대량 동시 폴링 부하 완화: **정확한 rank를 반환하되(ZRANK는 O(log N)로 저렴) 결과를 1~2초 TTL로 캐싱**해 폴링 폭주를 흡수한다(§9-D5). bucket 근사는 과설계로 채택하지 않는다.
  - status=READY가 되면 클라이언트는 폴링을 멈추고 주문 API로 전환한다.
- **Errors**: FR-2와 동일.

### 6.4 운영/관측 (선택)

#### FR-7. 대기열 현황 조회 (Admin, 선택)
- **What**: 총 대기 인원, 활성 인원, 현재 배치 크기/주기, 처리량 추정을 조회.
- **API(예상)**: `GET /api/v1/admin/waiting-queue/status`.
- **Rules**: 관측·튜닝 목적. 노출 범위/인증은 Open Question. 메트릭(Prometheus)으로도 노출 권장(week7 모니터링 자산 재사용).

## 7. 비기능 요구사항 (Non-functional)

> 아래는 요구사항에서 직접 도출된 항목만 기재한다.

- **NFR-1 (순서 보장)**: 대기열은 진입 순서(FIFO)를 보장해야 한다. 동시 진입 시에도 score/시퀀스로 결정적 순서를 유지한다.
- **NFR-2 (중복 진입 방지 / 멱등)**: 같은 유저의 반복 진입 요청은 순번을 새로 밀지 않는다(멱등).
- **NFR-3 (백프레셔 / admission control)**: 주문 API 유입은 시스템 처리량 이하로 제어한다. ~~활성 인원 `maxActive` 상한(정원제)~~ → **[방류형]** 활성 상한이 아니라 **방류 레이트(N/M)**로 제어한다. 방류 레이트를 지속 처리량 이하로 잡으면 유효 토큰 보유자 수(동시 부하)는 리틀의 법칙으로 `N/M × TTL`에 수렴한다.
- **NFR-4 (처리량 기반 방류 산정)**: ~~배치 크기 N과 maxActive~~ → **[방류형]** 방류 인원 N과 주기 M을 노브로 직접 산정하고 근거를 문서화한다. **확정값(§9-D2)**:
  - `release-size N = 30`, `scheduler-interval-seconds M = 2` → **throughput = N/M = 15 주문/초**(순간 방류 레이트).
  - N 산정 근거: HikariCP `maximum-pool-size = 40`(`modules/jpa/jpa.yml`)의 ~75%(=30)를 주문 동시 처리 예산으로 잡고, 나머지 25%는 조회·릴레이·리컨사일 헤드룸으로 예약. 방류형에선 이 30이 "상한 gate"가 아니라 "지속 처리 가능 동시성 목표"이며, `N/M × TTL ≲ 30`이 되도록 M·TTL을 맞춘다(현재 15/s × 30s TTL의 정상상태 동시 활성은 대기 소진 후 처리율에 수렴).
  - ~~`배치 N = min(N_max, maxActive − 현재 활성)`(정원제 리필)~~ → **[방류형]** 매 주기 대기열 앞에서 최대 N명 무조건 방류, 활성 점유량 무관. 실제 N·M·TTL은 부하테스트로 튜닝.
- **NFR-5 (스케줄러 단일 실행)**: 다중 인스턴스에서도 스케줄러 발급 로직은 중복 실행되지 않아야 한다(분산 락/리더 선출).
- **NFR-6 (토큰 만료 자동화)**: 미사용 토큰은 TTL로 자동 회수되어 활성 슬롯이 영구 점유되지 않는다.
- **NFR-7 (Polling 부하 관리)**: 대기 인원 증가 시 조회 API의 부하가 선형 폭증하지 않도록 캐싱/근사/폴링 주기 제어로 완화한다.
- **NFR-8 (장애 격리)**: Redis 장애 시 **fail-closed**로 신규 주문 진입을 차단(503)한다(§9-D7). 대기열은 백엔드 보호 장치이므로 우회(fail-open)를 허용하지 않는다. 이미 유효 토큰을 보유해 처리 중인 유저에 대한 영향은 최소화한다.

## 8. 정책 / 비즈니스 규칙

- **P-1. 관문 원칙**: 대기열은 주문 API 진입 자격만 통제한다. 주문 성공 여부·재고·결제 결과는 기존 로직이 판정하며, 대기열은 관여하지 않는다.
- **P-2. 1회용 토큰**: 토큰은 1회 주문 진입에만 유효하다. 주문 확정 시 삭제한다. (여러 번 주문 필요 시 재진입 정책은 Open Question.)
- **P-3. 순번 유지**: 이미 대기열에 있는 유저의 재진입은 순번을 유지한다(뒤로 밀지 않음).
- **P-4. 만료 후 재진입**: 토큰 만료 유저가 다시 주문하려면 대기열 뒤로 재진입한다(공정성). 특혜 없음.
- **P-5. ~~활성 상한 우선~~ → [방류형] 윈도우 레이트 우선**: ~~활성이 꽉 차면 발급 0(정원제)~~ → 스케줄러는 매 주기 최대 N명을 방류하되, 같은 M초 윈도우 방류 총합이 N을 넘지 않도록 Lua 윈도우 카운터로 제한한다(활성 점유량은 방류 결정에 관여 안 함).
- **P-6. 주문 이후 위임**: 토큰 검증 통과 후의 모든 흐름은 week6~week7 구조에 위임한다(신규 규칙 없음).

## 9. 가정 & 결정 사항 (Assumptions & Resolved Decisions)

작성 근거로 다음을 **확인**했다(코드/설정 검증 완료).
- 유저 식별은 기존 주차와 동일하게 요청 헤더 **`X-USER-ID`** 기반(주문 API 등에서 사용 중, 검증됨).
- 주문 생성 API는 **`POST /api/v1/orders`**(`OrderV1Controller`, 검증됨).
- 스케줄러 단일 실행은 이미 도입된 **ShedLock**(`SchedulerConfig`, `PaymentReconcileScheduler`)을 재사용(검증됨).
- 대기열은 **단일 글로벌 큐**(특정 이벤트/상품 구분 없음)로 시작하되, 키 네이밍은 향후 큐 분리가 가능하도록 설계.
- 실시간 조회는 요구사항 명시대로 **Polling** 한정. SSE/WebSocket은 범위 밖.

아래는 열린 질문에 대한 **초안 확정(Decision)** 이다. 각 항목에 결정과 근거를 기재한다. (추후 변경은 이 표만 갱신하면 된다.)

| # | 결정 | 근거 |
|---|------|------|
| **D1** 토큰 TTL | ~~60초~~ → **30초(개정)** | 초안은 60초였으나, TTL 스윕 시뮬레이션(→[`06`](./06-loadtest-ttl.md))에서 15% 이탈 가정하 **30초가 배수시간 최소·처리량 최고**로 나와 개정. TTL이 길면 이탈자가 슬롯을 오래 점유(squatting)해 처리량이 떨어지고, 너무 짧으면 느린 정상 유저가 바운스/실패한다. 최적 TTL은 이탈률에 민감하므로 실측 확보 시 재튜닝. |
| **D2** 방류 인원·주기 | ~~정원제: maxActive=30, N_max=30(활성까지 리필), throughput 60/s~~ → **[방류형] release-size N=30, interval M=2s → throughput = N/M = 15/s** | HikariCP 풀=40의 ~75%(=30)를 동시 처리 예산으로 잡되, 방류형에선 상한 gate가 아니라 방류 레이트로 제어(NFR-4). 정상상태 동시 부하 ≈ N/M×TTL. N·M·TTL은 부하테스트로 튜닝. |
| **D3** 주문 실패 시 토큰 | **즉시 회수 안 함, TTL까지 재시도 허용** | 일시적 실패(재고 순간부족·PG 타임아웃)로 유저를 대기열 뒤로 보내면 UX가 나쁘다. TTL이 어차피 버려진 토큰을 회수하므로 안전. **성공 확정 시에만** 즉시 삭제(1회용 원칙 P-2). |
| **D4** 토큰 전달 방식 | **헤더 `X-QUEUE-TOKEN`** | 기존 `X-USER-ID` 헤더 인증 컨벤션과 일관. 진입 자격은 인증성 메타데이터라 바디보다 헤더가 적절하고, 주문 요청 바디 스키마를 건드리지 않는다. |
| **D5** 순번 정밀도 | **정확 rank + 1~2초 캐싱** | `ZRANK`는 O(log N)로 저렴하다. bucket 근사는 과설계. 대신 조회 결과를 1~2초 TTL 캐싱해 대량 폴링을 흡수(Step 3 부하 요구 충족). |
| **D6** 활성/토큰 저장 구조 | **개별 키 TTL `pass:{token}`(토큰→유저 검증·자동만료) + 활성 ZSET `active:users`(score=만료시각) 병행** | ~~정원제: 활성 ZSET을 청소 후 ZCARD로 정확 카운트해 리필량 계산~~ → **[방류형]** 활성 ZSET은 리필량 계산에 안 쓴다(방류량은 Lua 윈도우 예산이 결정). 대신 (a) admin 관측 카운트, (b) 진입 시 이미 활성인 유저 O(1) 판정(재큐잉 방지)에만 사용. 만료 청소(`ZREMRANGEBYSCORE`)는 두 용도의 정확성 유지를 위해 존치. |
| **D7** Redis 장애 시 | **fail-closed(주문 진입 차단, 503)** | 대기열의 존재 이유가 백엔드 보호다. 장애 시 fail-open 하면 방어막이 사라져 폭주 → 원래 막으려던 장애를 자초한다. 이미 유효 토큰 보유 유저의 진행에는 영향 최소. 대기열 진입 불가는 503 안내. |
| **D8** Admin 현황 API | **최소 조회 1개(`GET /api/v1/admin/waiting-queue/status`) + Prometheus 메트릭 병행** | 배치 크기·주기를 튜닝하려면 실시간 대기/활성 인원 관측이 필수. week7 모니터링(Grafana/Prometheus) 자산 재사용. 무겁게 만들지 않는다. |
| **D9** 재진입/다회 주문 | **매 주문마다 대기열 재진입** | 공정성 정책(P-4)·1회용 토큰(P-2)과 일관. 한 번 통과했다고 무제한 주문 특혜를 주면 관문이 무력화된다. |

> 위 결정은 초안이며, 부하테스트(Step 2의 처리량 검증)에서 D1·D2 수치가 조정될 수 있다. 조정 시 이 표와 NFR-4를 함께 갱신한다.
