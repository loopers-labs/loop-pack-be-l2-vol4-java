# 트랜잭션 · 동시성 리뷰 (commerce-api)

이 스킬은 `apps:commerce-api` 의 트랜잭션 경계와 동시성 제어를 **유즈케이스 단위로** 읽고, 정합성·성능·교착 위험을 드러내 선택적 개선을 돕는다. 목표는 "이게 정답"이 아니라 "이 구조가 어떤 의도이고 어떤 비용을 지불하는가, 어디를 바꾸면 무엇이 좋아지고 무엇이 나빠지는가"를 명확히 하는 것이다.

전제: 이 프로젝트는 **MySQL 8.0 InnoDB** 를 쓰므로 JPA/Hibernate 는 별도 지정이 없으면 **REPEATABLE READ(RR)** 격리수준에서 동작한다. RR 의 특성이 락·정합성 판단의 기준선이므로, 분석 시 항상 RR 을 가정한다.

**이 스킬은 코드를 수정하지 않는다.** 산출물은 아래 "리포트 구조"의 진단 문서뿐이며, 개선은 강제 변경이 아니라 trade-off 와 함께 "제안"으로만 제시한다. 실제 코드 변경이 필요하면 사용자 승인을 받아 별도 작업(구현 시 `../ecommerce-implementation/SKILL.md`)으로 진행한다.

## 작업 전 확인

1. 분석 대상 유즈케이스(요청 흐름)를 먼저 정한다: Controller → Facade → Service → Repository 전체를 본다. 특정 메서드만 떼어 판단하지 않는다 — 트랜잭션·락은 흐름 전체의 속성이기 때문이다.
2. 프로젝트의 트랜잭션 배치 규칙은 [`.claude/rules/code-conventions.md`](../../rules/code-conventions.md) 의 "트랜잭션 규칙", 책임 배치는 [`.claude/rules/architecture.md`](../../rules/architecture.md) 를 기준으로 한다. 이 스킬은 그 규칙을 "위반했는지"가 아니라 "왜 그렇게 두었고 대안이 무엇인지"까지 본다.
3. 락 전략(비관적/낙관적)·격리수준이 코드/설정 어디에 드러나는지 찾는다. 명시가 없으면 RR + 비관적 락 부재(=동시성 미제어)를 의심한다.

> 이 스킬은 **리뷰(분석)** 전용이다. 코드를 새로 **구현**하는 단계라면 [`../ecommerce-implementation/SKILL.md`](../ecommerce-implementation/SKILL.md) 를 따른다. 점검 기준이 되는 구현 규칙은 그 스킬의 [`transaction.md`](../ecommerce-implementation/transaction.md)(트랜잭션 경계)와 [`concurrency.md`](../ecommerce-implementation/concurrency.md)(락 전략)에 정의되어 있으므로, 본 리뷰는 그 규칙을 근거로 현 구조의 trade-off 를 진단한다.

## 이 코드베이스의 기준 구현 (분석의 레퍼런스)

새 흐름을 분석할 때, 이미 정합성이 검증된 아래 구현과 대조하면 빠르다.

- **트랜잭션 경계는 Facade 단일 진입점.** `@Transactional` 은 `OrderFacade`, `CouponFacade`, `ProductFacade` 등 application 계층 Facade의 클래스 레벨에만 둔다. 조회 전용 메서드만 `@Transactional(readOnly = true)` 로 오버라이드한다. Domain Service(`OrderCreationService` 등)에는 트랜잭션을 두지 않고 호출자의 트랜잭션에 전파시킨다.
- **주문 생성의 정합성 핵심**(`OrderFacade.createOrder`)은 한 트랜잭션 안에서 (1) 재고 비관적 락 차감 → (2) 주문 생성·1차 저장 → (3) 쿠폰 비관적 락 사용 → (4) 할인·결제금액 확정 순으로 처리하고, 어느 단계가 실패해도 전체가 롤백된다.
- **재고 차감**: 독립 `Inventory` 애그리거트. `InventoryRepository.findAllByProductIdsForUpdate(...)` 가 `@Lock(PESSIMISTIC_WRITE)` 로 행을 잠근 뒤 `inventory.deduct(qty)` 로 차감한다. 변경은 Facade 트랜잭션의 dirty checking 으로 flush 된다.
- **쿠폰 1회 사용**: `MemberCouponRepository.findByIdForUpdate(...)` 가 `@Lock(PESSIMISTIC_WRITE)` 로 회원 쿠폰 행을 잠그고 상태(`AVAILABLE→USED`)를 전이시켜 동시 사용을 직렬화한다.
- **좋아요 정합성**: 락이 아니라 `product_like(member_id, product_id)` 유니크 제약으로 보장한다 — 서로 다른 회원은 충돌 없이 각자 저장, 동일 회원 중복은 제약으로 1건만 남는다.

이 패턴들이 "왜" 그렇게 되어 있는지는 아래 체크리스트의 RR·락 설명과 함께 읽는다.

## MySQL REPEATABLE READ 가 분석에 주는 기준선

RR 을 모르고 보면 "락을 왜 거나"를 오판한다. 핵심만:

- **순수 SELECT 는 MVCC 스냅샷 읽기**라 락을 걸지 않고, 트랜잭션 시작 시점의 일관된 스냅샷을 본다. 그래서 `read → 계산 → update` 패턴은 RR 이어도 **lost update 를 막지 못한다**. 두 트랜잭션이 같은 재고 10을 읽고 각각 -1 하면 둘 다 9로 덮어써 1개가 증발한다. 재고·쿠폰처럼 read-modify-write 가 있는 곳에 **명시적 잠금 읽기(`SELECT ... FOR UPDATE`)가 필요한 이유**가 이것이다.
- **`SELECT ... FOR UPDATE` 는 잠금 읽기(current read)** 로, 스냅샷이 아니라 최신 커밋 값을 읽고 행을 잠근다. 그래서 쿠폰을 `findByIdForUpdate` 로 읽으면 먼저 커밋된 `USED` 를 반드시 보고 두 번째 사용을 막을 수 있다.
- **RR 의 잠금 읽기는 next-key lock(레코드 + 직전 갭)** 을 잡는다. 인덱스를 탄 단건/유니크 조회면 사실상 레코드 락이지만, **인덱스를 못 타거나 범위/`IN` 조건이면 갭까지 잠가** 동시성이 의도보다 크게 떨어지거나 엉뚱한 삽입을 막을 수 있다. → `FOR UPDATE` 조회의 `WHERE` 절이 적절한 인덱스(PK·UK)를 타는지 반드시 확인한다. (예: `inventory.product_id`, `member_coupon.id` 는 인덱스가 있어 행 단위로 잠긴다.)
- **데드락은 "락 획득 순서가 트랜잭션마다 다를 때" 발생**한다. 여러 행을 잠그면 항상 같은 순서로 잠가야 한다. 기준 구현이 재고를 차감하기 전 `productId` 오름차순으로 정렬해 잠그는 이유다. 서로 다른 자원군(재고→쿠폰)도 흐름마다 같은 순서를 유지한다.
- **락은 트랜잭션이 커밋/롤백될 때까지 유지된다.** 즉 비관적 락을 잡은 트랜잭션이 길면(외부 API 호출, 무거운 조회 포함) 그 행을 기다리는 다른 주문이 그만큼 막힌다. → 잠금 구간은 짧게, 외부 호출은 트랜잭션 밖으로.

## 분석 체크리스트

흐름 하나를 받으면 아래 순서로 본다. 각 항목은 "문제다/아니다"가 아니라 "어떤 트레이드오프인가"를 적는다.

### 1. 트랜잭션 경계(Transaction Boundary)

- 트랜잭션이 어디서 시작되는가? (Facade 단일 진입점인가, Service/Controller 로 새는가?)
- 트랜잭션 안에서 실제로 수행되는 작업을 순서대로 나열한다. 각각이 **상태 변경(쓰기)** 인지 **단순 조회** 인지, **외부 호출** 인지, **반복문/대량 처리** 인지 분류한다.
- 비관적 락을 잡는 지점과, 그 락이 풀리는 시점(=트랜잭션 끝)까지의 "구간"을 표시한다. 이 구간이 길수록 경합 비용이 크다.

출력 예시:
```text
OrderFacade.createOrder()  [@Transactional]
  ├─ 회원 검증            (조회)
  ├─ 상품/브랜드 조회      (조회)
  ├─ 재고 FOR UPDATE 차감  (쓰기, 🔒 lock 시작 — productId asc)
  ├─ 주문 생성/저장        (쓰기)
  ├─ 쿠폰 FOR UPDATE 사용  (쓰기, 🔒 lock)
  └─ 할인/결제금액 확정    (쓰기)
                          ⤷ commit 시 🔒 모두 해제

트랜잭션이 꼭 필요한 핵심: 재고 차감 · 쿠폰 사용 · 주문 저장 (원자성)
```

### 2. 불필요하게 크거나 위험한 트랜잭션

아래가 있는지 본다(있으면 "왜 거기 있는지"와 분리 시 득실을 적는다):
- Controller/Domain Service 에 `@Transactional` 이 새어 있음.
- 읽기 전용 로직이 쓰기 트랜잭션에 섞여 `readOnly` 최적화·의도 표현을 놓침.
- **외부 시스템 호출(PG 결제, 알림 등)이 락을 든 트랜잭션 내부에 있음** — 외부 지연만큼 행 락이 유지되어 동시 주문이 직렬화된다. DB 트랜잭션과 외부 호출 경계를 분리할 후보.
- 트랜잭션 안에서 대량 조회/복잡한 QueryDSL 이 락 구간을 길게 늘림.
- 상태 변경 이후에도(예: 응답 조립용 추가 조회) 트랜잭션이 길게 유지됨.

### 3. 동시성 / 락(Concurrency)

이 흐름이 동시 요청에서 깨지지 않는지 본다:
- **read-modify-write 가 있는가?** 있으면 그 자원이 락(비관적 `FOR UPDATE`) 또는 `@Version`(낙관적) 또는 조건부 update 중 무엇으로 보호되는가? 아무것도 없으면 lost update / 초과 판매 위험.
- **비관적 vs 낙관적 선택의 근거가 자원 특성에 맞는가?** 단일 핫 로우(재고·쿠폰)에 경합이 잦고 "정확히 1회/초과금지"가 핵심이면 비관적이 단순·견고. 충돌이 드물고 재시도가 싸면 낙관적이 처리량에 유리. 이 프로젝트는 재고·쿠폰 모두 비관적을 선택했다(근거: 핫 로우 경합 + exactly-once).
- **락 획득 순서가 모든 경로에서 동일한가?** (데드락) — 다건 잠금은 정렬 후 잠그는지 확인.
- **`FOR UPDATE` 조회가 인덱스를 타는가?** RR next-key lock 으로 갭까지 잠가 과도한 직렬화/엉뚱한 차단이 없는지.
- **유니크 제약으로 충분한 자리에 락을 과하게 쓰진 않았는가?** (좋아요처럼 "중복만 막으면 되는" 멱등 케이스는 UK 가 더 싸다.)
- **낙관적 락 재시도/비관적 락 타임아웃 시 동작**이 정의되어 있는가(사용자에게 무엇이 보이나)?

> 함정 메모(이 프로젝트에서 실제로 겪음): 멱등 보장을 위해 저장을 `@Transactional(REQUIRES_NEW)` 로 감싸면, 외부 트랜잭션이 커넥션을 든 채 중첩 트랜잭션이 **두 번째 커넥션**을 요구한다. 동시 스레드 수 × 2 가 커넥션 풀 크기를 넘으면 풀 고갈로 일부 요청이 타임아웃 실패한다. 핫 패스의 멱등성은 가능하면 **DB 유니크 제약**으로 풀고 중첩 트랜잭션을 피한다.

### 4. JPA / 영속성 컨텍스트

- Entity 변경이 **언제 flush** 되는가? 기준 구현은 차감/상태전이를 managed entity 에 하고 **커밋 시 dirty checking flush** 에 맡긴다. 그러려면 그 작업이 반드시 **쓰기 트랜잭션 안**에 있어야 한다(분리/`readOnly` 시 변경이 사라진다).
- **조회용 Entity 가 변경 감지 대상이 되는가?** 단순 조회인데 Entity 를 들고 있다가 의도치 않게 수정→flush 될 여지가 있는지. 읽기는 `readOnly` 또는 DTO Projection 으로 변경 감지 비용·사고를 줄일 수 있다.
- **지연 로딩이 트랜잭션 후반/경계 밖에서 쿼리를 유발**하는가? (`open-in-view: false` 환경이라 경계 밖 접근은 `LazyInitializationException`.) N+1 가능성 있는 조회는 fetch join/`getMapByIds` 묶음 조회/QueryDSL 로.
- QueryDSL 조회 결과가 영속성 컨텍스트에 적재되어 불필요한 변경 감지·메모리 비용을 만드는가? 읽기 전용이면 projection 검토.

## 개선 제안(선택적)

강제하지 않고 trade-off 와 함께 선택지로 제시한다.
- **조회 ↔ 쓰기 분리**: 무거운 조회/응답 조립을 트랜잭션 밖 또는 별도 `readOnly` 트랜잭션으로 빼 락 구간 단축.
- **외부 호출을 트랜잭션 밖으로**: 결제/알림은 도메인 트랜잭션과 경계 분리(필요 시 이벤트/아웃박스). 락 보유 시간 단축 + 외부 실패와 DB 정합성 분리.
- **`@Transactional(readOnly = true)`**: 의도 표현 + 일부 최적화. 단 동시성 보호 수단은 아님(여전히 명시 락 필요).
- **락 전략 재검토**: 경합·재시도 비용을 따져 비관적↔낙관적 전환, 또는 조건부 update(`UPDATE ... SET qty=qty-? WHERE qty>=?`)로 락 없이 원자 차감.
- **멱등성은 제약으로**: 핫 패스 중복 방지는 유니크 제약 우선, 중첩 트랜잭션 지양(커넥션 풀 함정).
- **락 순서 표준화**: 다건 잠금은 항상 동일 키 순서로 정렬해 데드락 제거.

## 리포트 구조

분석 결과는 항상 아래 형식으로 정리한다(섹션이 비면 "해당 없음"이라고 적어 점검했음을 남긴다):

```markdown
# 트랜잭션·동시성 리뷰: <유즈케이스>

## 1. 트랜잭션 범위
<Facade 진입점 / 내부 단계 / 락 구간 트리>
```
