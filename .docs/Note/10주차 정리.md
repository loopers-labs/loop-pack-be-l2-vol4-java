# Round 10 — 학습 정리 (Spring Batch 랭킹 집계)

> [!abstract] 한 줄 요약
> 실시간 랭킹은 **이벤트가 올 때마다 Redis ZSET을 조금씩 갱신**하는 문제였다.
> 이번엔 **이미 쌓인 집계 테이블(`product_metrics`)을 통째로 다시 읽어, 조회 전용 판(MV)을 주기적으로 새로 굽는** 문제다.
> → 핵심은 "대량 데이터를 어떻게 **끊어서(chunk)** 안전하게 처리하고, 그 결과를 **조회에 최적화된 형태(MV)로 미리 만들어 두느냐**".

---

## 0. 출발점 — 왜 실시간이 아니라 배치인가

일간/시간 랭킹은 이미 **Redis ZSET**으로 실시간 처리 중이었다. 그런데 주간·월간은 성격이 다르다.

```
실시간(Redis)  : 이벤트 1건 → 점수 조금 더함 (증분, 항상 최신)
배치(Batch)    : 하루치 집계를 한 번에 다시 계산 → 판을 새로 구움 (주기적, 무거움)
```

- 주간/월간은 **매 조회마다 수십만 행을 실시간 합산할 수 없다** → 미리 계산해 **조회 전용 테이블(MV)**에 넣어둔다.
- "무거운 계산은 미리(배치), 조회는 가볍게(MV에서 바로 읽기)" — **읽기/쓰기 부하를 시간축으로 분리**하는 발상.

> [!note] 이번 주 아키텍처 지도
> ```
> 이벤트 → [streamer] → product_metrics(DB) + Redis ZSET
>                              │
>                    [batch] 읽어서 집계 ──→ MV(주간/월간 테이블)
>                                                   │
>                                    [api] period로 소스 선택해 조회
> ```
> 앱이 3개(streamer/batch/api)로 분리 → 각자 필요한 **도메인 사본을 따로 보유**(공용 모듈 강제 안 함)한다.

---

## 1. Spring Batch 핵심 개념

> Batch = "정해진 대량 작업을, 중간에 죽어도 이어서, 추적 가능하게" 돌리는 프레임워크.

| 개념 | 의미 | 비유 |
| --- | --- | --- |
| **Job** | 배치 작업 전체 단위 | 요리 한 상 |
| **Step** | Job을 이루는 단계 | 재료 손질 → 조리 |
| **JobRepository** | 실행 이력·상태를 DB(BATCH_*)에 기록 | 작업 일지 |
| **JobParameters** | 실행마다 주는 인자(같은 Job도 파라미터로 다르게) | 오늘 날짜/기간 |
| **Tasklet** | 단순 단일 작업(한 방에 끝) | "테이블 비우기" |
| **Chunk** | 대량 데이터를 N개씩 끊어 읽고→처리→쓰기 | 컨베이어벨트 |

- **파라미터 기반 동작**: `period=weekly|monthly`를 JobParameter로 받아 **하나의 Job으로 주간·월간 둘 다** 굴린다.
- 같은 파라미터로 같은 Job을 두 번 못 돌린다(JobInstance 중복) → 실행마다 **고유값(run)**을 넣거나 `RunIdIncrementer`로 인스턴스를 구분.

> [!tip] `@ConditionalOnProperty`로 Job을 켜고 끈다
> `spring.batch.job.name`이 특정 값일 때만 해당 JobConfig가 뜨게 하면, **한 배치 앱에 여러 Job**을 두고 실행 시 어떤 Job을 돌릴지 고를 수 있다.

---

## 2. Chunk-Oriented Processing — Reader / Processor / Writer

```
[Reader] 한 건 읽기 ──→ [Processor] 한 건 변환 ──→ (chunk-size 만큼 모이면) [Writer] 한 방에 쓰기
   product_metrics          점수 계산·rank 부여            MV에 batch insert
```

- **chunk-size 단위로 트랜잭션**이 잡힌다 → 100건 모아 커밋. 중간에 죽어도 커밋된 지점까지는 안전.
- 한 건씩 처리하되 **쓰기는 묶어서** → 메모리도 아끼고 DB 왕복도 줄인다.
- Tasklet(단발성)과 대비: **대량 반복 처리**에는 Chunk가 정석.

---

## 3. 이번 주 진짜 난관 — "Chunk는 스트리밍인데 TOP 100은 전역 순위"

> [!warning] 문제
> 우리 점수식은 `view·wv + like·wl + log10(1+sales)·wo` 처럼 **여러 카운트의 가중합**이다.
> → 단순 컬럼 하나로 정렬(ORDER BY) 할 수 없다.
> 그런데 TOP 100 순위는 **전체를 정렬해봐야** 나온다. Chunk는 데이터를 조금씩 흘려보내는 구조라, **청크를 넘나드는 전역 rank**를 매기기 까다롭다.

**검토한 두 갈래:**

| 방식 | 아이디어 | 대가 |
| --- | --- | --- |
| **A. Reader가 SQL로 점수순 정렬** ⭐ | native SQL로 점수식을 계산해 `ORDER BY score DESC LIMIT 100` → 이미 정렬된 채로 흘러옴. Processor는 흘러온 순서대로 rank 1,2,3… 부여 | 점수식이 **SQL(정렬)과 코드(저장) 두 곳**에 존재(의도적 결합) |
| B. 2단계 Step | Step1: 전체를 staging에 점수 적재 → Step2: 점수순으로 읽어 rank | staging 테이블·Step 추가로 복잡도↑ |

→ **A를 선택.** DB가 잘하는 일(정렬·LIMIT)은 DB에 맡기고, 앱은 rank 부여만.

> [!tip] rank는 어떻게 매기나
> Reader가 점수 내림차순으로 흘려주므로, **단일 스레드 Chunk**에서 Processor가 `AtomicInteger`로 `++rank`만 하면 된다.
> Processor를 `@StepScope`로 두면 **Step 실행마다 새 인스턴스** → 카운터가 0부터 다시 시작(멱등).

---

## 4. Materialized View (MV) — 조회 전용으로 미리 구운 판

> MV = "매번 계산하기 비싼 결과를, 미리 계산해 **테이블에 물질화(materialize)**해 둔 것."

- `mv_product_rank_weekly` / `mv_product_rank_monthly` : 주간·월간 TOP 100을 **상품·rank·score로 비정규화**해 저장.
- 조회 시 조인·집계 없이 **rank 순으로 페이지만 읽으면 끝** → 응답이 가볍다.

> [!important] 멱등 재적재 — "덮어쓰기로 만든다"
> 배치가 매번 **① 대상 MV를 비우고(clear step) → ② 새로 적재**한다.
> → 몇 번을 돌려도 결과가 같다(중복 없음). 실행 중 실패해도 다음 실행이 판을 새로 구우면 회복.
> Job = `[clearStep(Tasklet)] → [aggregateStep(Chunk)]` 2단계로 구성한 이유.

---

## 5. 점수 정책 재설계 — 이벤트 기반 ≠ 카운트 기반

기존 실시간 정책(streamer)은 **이벤트 1건**을 점수화했다:

```
orderScore(price, quantity) = wo × log10(1 + price×quantity)   // 주문 "금액"
```

그런데 배치가 읽는 `product_metrics`엔 **카운트만** 있다(`sales_count`). **금액이 없다.**

> [!note] 그대로 재사용 불가 → 카운트 기반으로 새로 설계
> ```
> score = view_count × wv
>       + like_count × wl
>       + log10(1 + sales_count) × wo   // "금액" 대신 "판매 건수"를 log로 정규화
> ```
> - 조회·좋아요는 선형, 판매는 `log10(1+n)`으로 **완만하게**(한 상품의 대량 판매가 전부를 부수지 않게).
> - **가중치(`ranking.weight`) 설정은 재사용** — 값은 공유, 계산식만 상황에 맞게 교체.
> - 컨벤션대로 batch가 자기 `RankingScorePolicy` 사본을 보유(streamer 것과 별개).

## 6. API 확장 — period로 소스를 가른다

```
GET /api/v1/rankings?period=daily|weekly|monthly

daily   → Redis ZSET (기존, 실시간)
weekly  → mv_product_rank_weekly (MV, DB)
monthly → mv_product_rank_monthly (MV, DB)
```

- daily는 rank를 조회 위치(offset+i+1)로 계산하지만, **MV는 rank가 이미 저장돼 있어** 그대로 쓴다(더 정확).
- 잘못된 `period` → `CoreException(BAD_REQUEST)` → 400.
- `period` 미지정 시 기본 daily → **기존 API 하위호환** 유지(회귀 테스트로 확인).

## 7. 내가 내린 Trade-off (회고 소재)

> [!warning] ① `product_metrics`에 날짜 차원이 없다
> 테이블이 **상품당 누적 1행**(product_id UNIQUE)이라 "지난 7일"을 뽑을 수 없다.
> → 과제 단순화로 **"현재 스냅샷을 재집계"** 채택. 정직한 한계: 지금은 가중치가 같으면 **주간·월간 순위가 동일**해진다.
> → 실무화하려면 **일자별 스냅샷 테이블**(product_id, metric_date, counts)이 선행돼야 하고, 배치는 `WHERE metric_date BETWEEN d-6 AND d` 로 SUM 하게 된다.

> [!warning] ② 점수식이 두 곳에 산다
> 정렬용 SQL과 저장용 `RankingScorePolicy`가 **같은 식을 각자** 갖는다. 둘이 어긋나면 순위가 틀어진다 → 코드에 주석으로 결합을 명시. (B안이었다면 이 중복은 없앨 수 있었음 — 복잡도와 맞바꾼 선택)

> [!note] ③ `rank`는 MySQL 8 예약어
> 컬럼명으로 쓰면 DDL 실패 → 자바 필드는 `rank`, 컬럼은 `rank_no`로 매핑.

---

## 8. 앱 분리 구조가 강제한 것

> streamer / batch / api가 **각자 도메인 사본**을 갖는 컨벤션(예: `RankingKey`도 앱마다 복제).

- MV 엔티티도 **batch(쓰기용)·api(읽기용)가 같은 테이블을 각자 매핑** → 공용 모듈을 새로 만들지 않음.
- 장점: 앱 간 결합↓, 배포 독립성↑. 대가: **같은 개념의 사본이 늘어나** 변경 시 동기화 부담(점수식 중복과 같은 결).

## 전체 그림

```
product_metrics (일간 집계, DB)
   │  [batch: period=weekly|monthly]
   ▼
[clearStep] MV 비우기 ─→ [aggregateStep]
                          Reader(SQL 점수순 LIMIT 100)
                            → Processor(rank 부여 + 정책 점수)
                              → Writer(MV 적재)
   ▼
mv_product_rank_weekly / monthly  (조회 전용)
   │  [api: ?period=weekly|monthly]
   ▼
저장된 rank 순으로 페이지 조회 → 상품정보 조합 → 응답
```

> **실시간(Redis)은 "지금 이 순간"을, 배치(MV)는 "정해진 기간의 확정 판"을 책임진다.**
> 무거운 집계를 조회 경로에서 걷어내 **미리·한 번에** 굽고, 조회는 그 판을 **가볍게 읽기만** 하도록 시간축으로 분리하는 것 — 그게 Round 10이다.
