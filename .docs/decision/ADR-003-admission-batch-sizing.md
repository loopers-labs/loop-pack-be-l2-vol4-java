# ADR-003 — 주문 대기열 입장 스케줄러 배치 크기 산정

- **Status**: Accepted
- **Date**: 2026-07-08

---

## Context

블랙 프라이데이 트래픽(평소 100 TPS → 순간 10,000 TPS)으로부터 주문 API 하류(DB·PG)를 보호하기 위해, 주문 API 앞단에 Redis Sorted Set 대기열을 두고 스케줄러(`QueueAdmissionScheduler`)가 주기적으로 앞 N명을 꺼내 입장 토큰을 발급한다(`AdmissionService.admit(batchSize)`). 이때 **한 번에 몇 명을(batch-size), 얼마마다(interval) 입장시킬지**를 정해야 한다.

이 숫자는 임의값이 아니라 **하류가 감당 가능한 처리량(back-pressure)** 에서 유도된다. 너무 크면 대기열을 두고도 하류가 터지고(Thundering Herd), 너무 작으면 유저 대기 시간이 불필요하게 길어진다.

## Decision

- **batch-size = 18** (`queue.admission.batch-size`)
- **interval = 100ms** (`queue.admission.interval`, `@Scheduled(fixedDelay)`)
- 즉 **초당 약 180명** 입장 (≈ 목표 175 TPS).

### 산정식

```
DB 커넥션 풀:              50
주문 1건 평균 처리 시간:    200ms
→ 이론상 최대 TPS:         50 / 0.2s = 250 TPS
→ 안전 마진 70% 적용:      250 × 0.7 ≈ 175 TPS
→ interval 100ms 로 분산:  175 / 10 ≈ 18명 / 100ms
```

### 판단 ① — 왜 이론 최대치(250)가 아니라 70% 마진(175)인가

이론상 250 TPS는 **모든 커넥션이 200ms에 정확히 반납된다는 이상 가정** 위의 값이다. 현실에서는:

- **지연 변동**: 주문 API 지연이 커지면 커넥션 점유 시간이 200ms를 넘겨, 실질 처리량이 250보다 낮아지고 타임아웃 위험이 커진다.
- **풀은 공유 자원**: 커넥션 풀 50개는 주문 전용이 아니다. 주문이 50개를 모두 점유하면 다른 API가 커넥션 기아(starvation)에 빠진다.

따라서 이론 최대치를 100% 쓰지 않고 **30% 여유를 남겨** 지연 변동과 타 API 몫을 흡수한다. 70%는 SLO가 아니라 **가정에 기반한 보수적 계수**다.

### 판단 ② — 왜 "1초에 175명 한 번"이 아니라 "100ms마다 18명"인가

- 175명을 **한 순간에** 입장시키면 175개의 주문이 동시에 커넥션을 점유해 순간 부하 스파이크 → **Thundering Herd**(원래 문제의 축소판)가 재현된다.
- 100ms로 쪼개면 **평균 처리량(175/s)은 동일**하되, *순간(instantaneous) 피크*가 약 10배 평탄해진다. 총량을 줄이는 게 아니라 **버스트를 시간축에 흩뿌리는** 것이 핵심이다.

## Consequences

- 대기열이 back-pressure 밸브로 동작: 유입이 아무리 커도 하류에는 초당 ~180명만 흘러간다(시스템 안정).
- 한 100ms 창 안에서 18명이 같은 순간에 몰리는 **잔여 버스트**는 완전히 사라지지 않는다. 필요 시 토큰 활성화에 **Jitter(0~2초 랜덤 딜레이)** 를 부여해 창 내부까지 분산할 수 있다(Nice-to-have, 현재 미구현).
- 토큰 미사용(만료) 시 유효 처리량이 목표보다 낮아질 수 있어, 만료분만큼 추가 발급이 필요해질 수 있다(`Token Expiry Rate` 지표로 관측).

## 재검토 트리거 (이 숫자는 상수가 아니라 가정의 함수)

아래 가정이 바뀌면 batch-size·interval을 다시 계산한다.

| 가정 | 현재 값 | 바뀌면 |
| --- | --- | --- |
| DB 커넥션 풀 크기 | 50 | 풀 확장/축소 시 이론 TPS 재산정 |
| 주문 1건 평균 처리 시간 | 200ms | p99 지연 악화 시 실질 TPS 하락 → 마진 재검토 |
| 커넥션 풀을 주문만 쓰는가 | 아니오(공유) | 전용 풀 분리 시 마진 상향 여지 |
| 토큰 만료율 | — | >30%면 유효 처리량 출렁 → 발급량/토큰 TTL 재조정 |

## 관련 결정 (미해결·후순위)

- **#8 Graceful Degradation** (DEFERRED): Redis 장애 시 전면차단/우회/폴백 중 사전 정의 필요.
- **#10 pop+발급 원자성** (DEFERRED): `ZPOPMIN` 후 토큰 발급 실패 시 유저 유실. 현재는 `AdmissionService`가 유실을 `log.warn`으로 관측 가능하게만 남긴다. Lua 원자화 또는 processing 셋 이동으로 신뢰성 보강 여지.
