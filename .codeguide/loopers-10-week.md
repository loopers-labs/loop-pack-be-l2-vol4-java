# Round 10 Quests

## 목표

이전 주차에서 적재한 `product_metrics` 일간 집계 정보를 기반으로 주간, 월간 랭킹을 제공한다.

Spring Batch로 대량 집계를 처리하고, 조회 전용 Materialized View 성격의 테이블에 TOP 100 랭킹을 저장한 뒤 기존 Ranking API에서 일간, 주간, 월간 랭킹을 조회할 수 있게 확장한다.

## 핵심 범위

### Must-Have

| 항목 | 구현 목표 |
| --- | --- |
| Spring Batch | 파라미터 기반으로 주간, 월간 랭킹 집계 Job을 실행한다. |
| Batch Processing | `product_metrics`를 Chunk-Oriented 방식으로 읽고 집계한다. |
| Materialized View | 집계 결과를 조회 전용 테이블에 저장하고 Ranking API의 조회 원천으로 사용한다. |

## 전체 흐름

1. `product_metrics`에 일간 상품 메트릭이 적재되어 있다.
2. Spring Batch Job이 집계 기준일과 기간을 파라미터로 받아 실행된다.
3. Reader가 대상 기간의 `product_metrics` 데이터를 읽는다.
4. Processor가 상품별 주간 또는 월간 점수를 계산한다.
5. Writer가 TOP 100 결과를 조회 전용 테이블에 저장한다.
6. Ranking API는 요청 기간에 따라 일간 랭킹 또는 주간/월간 MV 테이블을 조회한다.

## Step 1. Spring Batch Job 구현

### 요구사항

- 하루치 메트릭 테이블인 `product_metrics`를 기반으로 주간, 월간 집계 데이터를 만든다.
- 대량 데이터를 처리할 수 있도록 Chunk-Oriented Processing을 사용한다.
- Batch Job은 파라미터 기반으로 동작해야 한다.
- Job 이름, 파라미터명, 실행 주기는 구현 전 별도 확정이 필요하다.

### 구현 체크리스트

- [ ] Spring Batch 의존성과 실행 설정을 구성한다.
- [ ] JobParameter로 집계 기준일과 집계 기간을 전달받는다.
- [ ] `product_metrics`를 읽는 Reader를 작성한다.
- [ ] 상품별 랭킹 점수를 계산하는 Processor를 작성한다.
- [ ] 집계 결과를 저장하는 Writer를 작성한다.
- [ ] 동일 파라미터 재실행 시 결과가 중복 적재되지 않도록 처리한다.

## Step 2. Materialized View 설계

### 요구사항

- 주간, 월간 TOP 100 랭킹을 조회 전용 테이블에 저장한다.
- 저장된 결과는 Ranking API가 빠르게 조회할 수 있어야 한다.
- 집계 기준 기간, 순위, 상품 ID, 점수는 조회에 필요한 최소 정보로 고려한다.

### 조회 전용 테이블

| 테이블 | 목적 |
| --- | --- |
| `mv_product_rank_weekly` | 주간 TOP 100 상품 랭킹 저장 |
| `mv_product_rank_monthly` | 월간 TOP 100 상품 랭킹 저장 |

### 설계 체크리스트

- [ ] 주간/월간 랭킹 테이블의 컬럼과 제약조건을 확정한다.
- [ ] 집계 기준일 또는 기간을 식별할 수 있는 기준 컬럼을 둔다.
- [ ] 상품별 순위와 점수를 저장한다.
- [ ] 조회 패턴에 맞는 인덱스를 설계한다.
- [ ] Batch 재실행 시 기존 결과를 교체할지, upsert할지 정책을 확정한다.

## Step 3. Ranking API 확장

### 요구사항

- 기존 Ranking API에서 일간, 주간, 월간 랭킹을 제공한다.
- 기존 일간 랭킹 조회 흐름은 유지한다.
- 주간, 월간 요청은 Batch가 저장한 조회 전용 테이블을 기반으로 응답한다.
- 기간 파라미터명과 응답 DTO 변경 여부는 API 계약이므로 구현 전 확정이 필요하다.

### API 기준

| 항목 | 기준 |
| --- | --- |
| 기존 API | `GET /api/v1/rankings?date=yyyyMMdd&size=20&page=0` |
| 확장 방향 | 요청 기간 정보에 따라 일간, 주간, 월간 랭킹을 구분한다. |
| 일간 조회 원천 | 기존 실시간 랭킹 저장소 |
| 주간/월간 조회 원천 | `mv_product_rank_weekly`, `mv_product_rank_monthly` |

### API 체크리스트

- [ ] 일간, 주간, 월간 랭킹 요청을 구분한다.
- [ ] 요청 기간에 맞는 조회 원천을 선택한다.
- [ ] 기존 Ranking API 응답 형태를 최대한 유지한다.
- [ ] 주간/월간 랭킹에도 상품 정보를 조합해 반환한다.
- [ ] 잘못된 기간 값이나 조회 불가능한 날짜에 대한 응답 정책을 정한다.

## 검증 체크리스트

| 검증 항목 | 확인할 내용 |
| --- | --- |
| Batch 실행 | JobParameter에 따라 주간, 월간 집계 Job이 실행되는지 확인한다. |
| Chunk 처리 | 대량 `product_metrics`를 Chunk-Oriented 방식으로 처리하는지 확인한다. |
| 집계 정확성 | 입력 메트릭 대비 상품별 점수와 순위가 의도대로 계산되는지 확인한다. |
| TOP 100 저장 | 주간/월간 테이블에 상위 100개만 저장되는지 확인한다. |
| 재실행 안정성 | 같은 기준 기간으로 재실행해도 중복 데이터가 생기지 않는지 확인한다. |
| API 분기 | 일간, 주간, 월간 요청이 각각 올바른 저장소를 조회하는지 확인한다. |
| 페이징 | `page`, `size` 기준으로 응답 범위가 올바르게 잘리는지 확인한다. |

## 구현 시 유의사항

- `product_metrics`는 일간 집계 원천으로 보고, 주간/월간 랭킹은 조회 최적화용 read model로 분리한다.
- Batch 재실행 정책은 데이터 정합성에 직접 영향을 주므로 삭제 후 재적재, upsert, 버전 관리 중 하나를 먼저 확정한다.
- API 기간 파라미터명, DTO 변경, MV 컬럼, 인덱스, 점수 계산식은 설계 결정이므로 구현 전에 별도로 합의한다.
- 주간/월간 랭킹 조회에서 상품 정보 N+1 조회가 발생하지 않도록 상품 ID 목록 기반 조회를 우선한다.
- 기존 일간 랭킹 API의 동작을 깨지 않도록 회귀 테스트를 함께 작성한다.
