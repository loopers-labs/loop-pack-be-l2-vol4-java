# Round 8 Quests

## 목표

트래픽이 폭증하는 순간에도 주문 API를 보호하면서 사용자에게 공정한 대기 경험을 제공한다.

Redis 기반 대기열로 주문 진입 처리량을 제어하고, 입장 토큰과 순번 조회를 통해 사용자가 대기 상태를 확인할 수 있는 주문 흐름을 만든다.

## 핵심 범위

### Must-Have

| 항목 | 구현 목표 |
| --- | --- |
| Redis Sorted Set 기반 대기열 | 진입 순서를 보장하고 userId 기준 중복 진입을 방지한다. |
| 입장 토큰 발급 및 검증 | 스케줄러가 대기열에서 허용 인원을 꺼내 TTL이 있는 입장 토큰을 발급한다. |
| 스케줄러 기반 순차 입장 | 처리량 기준으로 산정한 배치 크기만큼 주문 진입을 허용한다. |
| Polling 기반 순번 조회 API | 사용자가 현재 순번과 예상 대기 시간을 조회할 수 있게 한다. |

### Nice-To-Have

| 항목 | 기대 효과 |
| --- | --- |
| SSE 기반 실시간 순번 Push | 사용자의 polling 요청 수를 줄이고 대기 경험을 개선한다. |
| Polling 주기 동적 조절 | 순번 구간에 따라 polling 빈도를 조절해 부하를 낮춘다. |
| Thundering Herd 완화 | 발급 간격 분산 또는 jitter로 동시에 몰리는 주문 진입을 완화한다. |
| Graceful Degradation | Redis 장애 시 fallback 정책으로 서비스 저하를 통제한다. |

## 전체 흐름

1. 사용자는 주문 API 호출 전 대기열 진입 API를 호출한다.
2. 서버는 Redis Sorted Set에 userId를 등록하고 진입 순서를 관리한다.
3. 사용자는 polling으로 현재 순번과 예상 대기 시간을 조회한다.
4. 스케줄러는 일정 주기마다 대기열에서 N명을 꺼내 입장 토큰을 발급한다.
5. 주문 API는 입장 토큰이 있는 사용자만 통과시킨다.
6. 주문 완료 후 입장 토큰을 삭제한다.
7. 주문 API 이후 이벤트 발행, Kafka 파이프라인, Metrics 집계는 Round 7에서 구축한 구조를 그대로 활용한다.

## Step 1. Redis 기반 대기열

### 요구사항

- 블랙 프라이데이 행사처럼 주문 트래픽이 급증하는 상황을 전제로 주문 API 앞단에 대기열을 둔다.
- Redis Sorted Set을 사용해 먼저 진입한 사용자가 먼저 입장할 수 있게 한다.
- userId 기준으로 이미 대기열에 들어온 사용자의 중복 진입을 방지한다.
- 사용자는 대기열 진입 후 자신의 순번과 예상 대기 시간을 조회할 수 있다.

### API 체크리스트

- [x] 대기열 진입 API 구현: `POST /api/v1/queue/enter`
- [x] 순번 조회 API 구현: `GET /api/v1/queue/position`
- [x] userId 기반 중복 진입 방지
- [x] 전체 대기 인원 조회

## Step 2. 입장 토큰과 스케줄러

### 요구사항

- 스케줄러는 일정 주기로 대기열에서 N명씩 꺼내 입장 토큰을 발급한다.
- 입장 토큰에는 TTL을 둔다. 예: 5분
- 토큰이 있는 사용자만 주문 API에 진입할 수 있다.
- 주문 완료 후 토큰을 삭제한다.
- DB 커넥션 풀, 평균 주문 처리 시간, 목표 안정 처리량을 바탕으로 스케줄러 배치 크기를 산정하고 근거를 문서화한다.

### 구현 체크리스트

- [x] 스케줄러가 주기적으로 대기열에서 N명을 꺼내 입장 토큰 발급
- [x] 토큰 TTL 설정
- [x] 주문 API 진입 시 토큰 검증
- [x] 주문 완료 후 토큰 삭제
- [x] 처리량 기준으로 스케줄러 배치 크기 산정 근거 문서화

## Step 3. 실시간 순번 조회

### 요구사항

- 사용자가 대기 중 현재 순번과 예상 대기 시간을 확인할 수 있는 API를 구현한다.
- 기본 구현은 polling 기반으로 한다.
- 대기 인원이 많을 때 polling 요청 자체가 부하가 될 수 있으므로 응답에 권장 재조회 시간을 포함한다.
- 토큰이 발급된 사용자는 순번 조회 응답에서 입장 가능 상태와 토큰을 확인할 수 있게 한다.

### 구현 체크리스트

- [x] 예상 대기 시간 계산 로직 구현
- [x] Polling 기반 순번 및 예상 대기 시간 응답
- [x] 토큰 발급 시 순번 조회 응답에 토큰 포함
- [x] 대기 인원에 따른 polling 부하 고려

## 검증 체크리스트

| 검증 항목 | 확인할 내용 |
| --- | --- |
| 동시 진입 테스트 | 완료. 여러 사용자가 동시에 진입해도 대기열 순서가 보장되는지 확인한다. |
| 중복 진입 테스트 | 완료. 같은 userId가 여러 번 진입해도 대기열에 중복 등록되지 않는지 확인한다. |
| 토큰 만료 테스트 | 완료. TTL이 지난 입장 토큰이 주문 API에서 거부되는지 확인한다. |
| 토큰 삭제 테스트 | 완료. 주문 완료 후 토큰이 삭제되어 재사용되지 않는지 확인한다. |
| 처리량 초과 테스트 | 완료. 스케줄러 배치 크기 이상의 요청이 들어와도 초과 사용자가 WAITING으로 남고 시스템 진입이 제한되는지 확인한다. |

## 구현 시 유의사항

- 대기열은 주문 API 앞단의 관문으로만 둔다.
- 주문 생성 이후의 이벤트 발행, Kafka 파이프라인, Metrics 집계는 Round 7 구조를 재사용한다.
- Redis 장애 fallback, SSE, polling 주기 동적 조절, jitter는 기본 구현 완료 후 선택적으로 확장한다.
- 저장/연동 기술 추가나 장애 정책 변경은 구현 전 영향 범위와 검증 방법을 먼저 합의한다.
