# Round 9 Quests

## 목표

이전 주차에서 Kafka Consumer로 적재하던 `product_metrics` 집계 정보를 활용해 실시간 랭킹 파이프라인을 만든다.

Redis Sorted Set을 사용해 조회, 좋아요, 주문 이벤트 점수를 일간 랭킹에 누적하고, 이 랭킹을 기반으로 오늘의 인기 상품 API를 제공한다.

## 핵심 범위

### Must-Have

| 항목 | 구현 목표 |
| --- | --- |
| Redis Sorted Set | 날짜별 랭킹 키에 상품 점수를 누적하고 TTL을 관리한다. |
| Realtime Ranking | Kafka Consumer가 상품 이벤트를 소비해 랭킹 점수를 실시간에 가깝게 반영한다. |
| Ranking API | 랭킹 목록 조회와 상품 상세 조회에서 랭킹 정보를 제공한다. |

### Nice-To-Have

| 항목 | 기대 효과 |
| --- | --- |
| Kafka 배치 리스너 | 단건 처리보다 Redis, DB 연산 횟수를 줄이고 처리량을 높인다. |
| 시간 단위 랭킹 | 일간 랭킹보다 더 빠르게 변하는 초실시간 랭킹을 제공한다. |
| Weight 실시간 조절 | 운영 상황에 따라 조회, 좋아요, 주문 가중치를 조정할 수 있게 한다. |
| 콜드 스타트 완화 | Score Carry-Over로 날짜 변경 직후 빈 랭킹판 문제를 줄인다. |

## 전체 흐름

1. 상품 조회, 좋아요, 주문 이벤트가 Kafka topic으로 발행된다.
2. 랭킹 Consumer가 이벤트를 소비한다.
3. Consumer는 이벤트 종류별 weight와 score를 계산한다.
4. Redis Sorted Set `ranking:all:{yyyyMMdd}`에 상품별 점수를 누적한다.
5. Ranking API는 Redis 랭킹을 조회하고 상품 정보를 조합해 응답한다.
6. 상품 상세 조회 API는 해당 상품의 일간 순위를 함께 반환한다.

## Step 1. Kafka Consumer에서 Redis ZSET 적재

### 요구사항

- 조회, 좋아요, 주문 이벤트를 소비해 일간 랭킹 점수를 누적한다.
- 이벤트 발생일 기준으로 랭킹 키를 계산한다.
- 같은 상품에 여러 이벤트가 발생하면 Redis `ZINCRBY`로 점수를 더한다.
- 랭킹 데이터는 2일 TTL을 가진다.
- 날짜별 랭킹 키는 `ranking:all:{yyyyMMdd}` 형식을 사용한다.

### 점수 계산 예시

| 이벤트 | Weight | Score | 비고 |
| --- | ---: | ---: | --- |
| 조회 | 0.1 | 1 | 단순 노출보다 낮은 영향도로 반영한다. |
| 좋아요 | 0.2 | 1 | 선호 의사를 조회보다 높게 반영한다. |
| 주문 | 0.6 | `price * amount` | 필요하면 `log` 정규화로 고가 상품 쏠림을 줄인다. |

### 구현 체크리스트

- [x] 랭킹 ZSET의 TTL과 키 전략을 구성한다.
- [x] 이벤트 발생일 기준으로 날짜별 적재 키를 계산한다.
- [x] 이벤트 종류별 weight와 score 계산 규칙을 구현한다.
- [x] 이벤트 소비 후 ZSET 점수가 의도대로 반영된다.
- [x] 중복 이벤트 소비 가능성을 고려해 멱등성 기준을 정한다.

## Step 2. Ranking API 구현

### 요구사항

- 랭킹 목록 조회 API를 제공한다.
- Redis에서 상품 ID와 순위를 조회한 뒤 상품 정보를 조합해 응답한다.
- 상품 상세 조회 시 해당 상품의 랭킹 정보를 함께 반환한다.
- 랭킹에 없는 상품의 순위는 `null`로 반환한다.
- 프로젝트 페이징 기준은 0-based `page`를 사용한다.

### API 체크리스트

- [x] 랭킹 목록 조회 API 구현: `GET /api/v1/rankings?date=yyyyMMdd&size=20&page=0`
- [x] 랭킹 목록 조회 시 상품 ID만 반환하지 않고 상품 정보를 함께 제공한다.
- [x] 랭킹 목록 조회 시 rank, score, product 정보를 함께 제공한다.
- [x] 상품 상세 조회 응답에 해당 상품의 순위를 추가한다.
- [x] 랭킹에 없는 상품의 순위는 `null`로 반환한다.

## Step 3. 추가 개선

### Kafka 배치 리스너

- 단건 소비가 많은 ZSET 연산과 DB 조회를 유발하면 배치 리스너를 검토한다.
- 같은 배치 안에서 상품별 점수를 먼저 합산한 뒤 Redis에 반영한다.
- 상품 정보 조회가 필요하면 상품 ID를 모아 bulk 조회한다.

### 시간 단위 랭킹

- 일간 키와 별도로 시간 단위 키를 둔다.
- 예: `ranking:all:{yyyyMMddHH}`
- TTL, 조회 API 파라미터, 일간 랭킹과의 관계를 별도로 정한다.

### Weight 실시간 조절

- weight를 코드 상수로 고정할지, 설정값으로 둘지 결정한다.
- 운영 중 변경 가능한 설정으로 둘 경우 변경 이력과 적용 시점을 기록한다.
- 과거 점수 재계산이 필요한지 여부를 함께 정한다.

### 콜드 스타트 완화

- 날짜 변경 직후 랭킹이 비어 있는 문제를 줄이기 위해 Score Carry-Over 스케줄러를 검토한다.
- 예: 23시 50분에 오늘 랭킹 상위 상품 일부를 내일 랭킹 키로 이월한다.
- Carry-Over 비율, 대상 개수, TTL 정책을 함께 정한다.

## 검증 체크리스트

| 검증 항목 | 확인할 내용 |
| --- | --- |
| 이벤트 반영 | 이벤트 발행 후 Redis ZSET 점수가 반영되는지 확인한다. |
| 랭킹 조회 | ZSET 점수 순서대로 랭킹 API 응답이 반환되는지 확인한다. |
| 상품 정보 조합 | 랭킹 API가 상품 ID뿐 아니라 상품 정보를 함께 제공하는지 확인한다. |
| 상세 순위 | 상품 상세 조회 시 해당 상품의 순위가 함께 반환되는지 확인한다. |
| 순위 없음 | 랭킹에 없는 상품은 순위가 `null`로 반환되는지 확인한다. |
| 날짜 변경 | 일자가 변경되어도 이전 날짜 랭킹 조회가 정상 동작하는지 확인한다. |
| 가중치 | 주문 1건이 좋아요 3건보다 높은 점수로 반영되는지 확인한다. |
| TTL | 랭킹 키가 2일 TTL로 관리되는지 확인한다. |

## 구현 시 유의사항

- 기존 `product_metrics` 적재 흐름과 Kafka Consumer 구조를 우선 재사용한다.
- Redis ZSET은 랭킹 조회 최적화를 위한 read model로 보고, 원천 이벤트와 집계 기준을 분리해 생각한다.
- 랭킹 점수 계산식은 테스트로 고정해 weight 변경 시 영향이 드러나게 한다.
- 상품 정보 조합 시 N+1 조회가 발생하지 않도록 상품 ID 목록 기반 조회를 우선한다.
- 배치 리스너, 시간 단위 랭킹, Weight 실시간 조절, Carry-Over는 기본 랭킹 파이프라인 완료 후 선택적으로 확장한다.
